# hyprv — significant decisions

Settled calls documented so a fresh agent doesn't second-guess them. **This stays referenced** — read it before reworking an area. Index: [`../PLAN.md`](../PLAN.md).
- **Folder/project naming**: `hyprv-app/` was renamed to `hyprv/` and `hyprv-app.vcxproj` → `hyprv.vcxproj`; the whole source tree was then nested under `src/` (`src/app/`, `src/rdphost/`, `src/shared/`, `src/resources/`) for a more conventional cross-platform C++ layout. The C++/WinRT projection namespace stays `winrt::hyprv_app::implementation` — see CLAUDE.md "Project naming (subtle — do not 'fix')". Attempting to rename the projection to `winrt::hyprv::` creates a name collision with our internal `::hyprv::` namespaces; was attempted, broke MSVC, was reverted. The `_app` suffix is permanent.
- **Build output layout**: `bin/` lives at the repo root (next to `src/`) so the deliverables sit at the obvious spot — `bin/x64/Debug/{hyprv,hyprv-rdphost}.exe`. Intermediate files (`.obj`, `.pch`, MIDL/cppwinrt generated headers, unmerged winmds) go under `src/obj/<project>/x64/<Config>/`. Both `bin/` and `src/obj/` are gitignored. The vcxprojs use `$(SolutionDir)bin\…` and `$(SolutionDir)src\obj\…` — never build a vcxproj directly (`$(SolutionDir)` would resolve to the project dir instead of the repo root).
- **JSON for settings**: `Windows::Data::Json` (already linked via WinRT) instead of `nlohmann::json`. Schema is small enough that the ergonomic loss is offset by avoiding a 1MB header. Revisit if the schema gets complex.
- **Settings + log location**: the REAL `%LOCALAPPDATA%\hyprv\` (settings.json + hyprv.log are intentional persisted state). Resolved via `SHGetKnownFolderPath(FOLDERID_LocalAppData, KF_FLAG_NO_PACKAGE_REDIRECTION | KF_FLAG_CREATE)`. Under MSIX, BOTH a path redirect (the known-folder API returns the package LocalCache without the flag) AND a write redirect (AppData write-virtualization) apply — so the flag fixes the path and the manifest (`unvirtualizedResources` + `FileSystemWriteVirtualization` exclusion for `$(KnownFolder:LocalAppData)\hyprv`) disables the write redirect. Both halves are required; either alone silently lands the file in LocalCache. Unpackaged/Debug builds are never redirected (the flag is a no-op there). [Decided this session — the earlier "MSIX virtualizes into LocalState, works seamlessly" note was wrong: it lands in LocalCache and is hard to find.]
- **Log share mode**: `_SH_DENYWR` so external tools (tail, notepad, VS Code) can read while hyprv writes.
- **No external dep policy**: NuGet packages we already depend on (WindowsAppSDK, WebView2, etc.) are fine; new third-party libraries need a stronger justification. We're keeping the bar high here.
- **Out-of-process rdphost is non-negotiable**: don't propose collapsing it back in-process even if it'd save IPC complexity. mstscax leaks; this architecture is the whole point.
- **Window-restore ordering in `MainWindow::OnActivated`**: `ResolveWindowHwnd` → `ApplyPersistedGeometry` → `AttachWindowSubclass` → `ExtendIntoTitleBar`. The middle two MUST be in that order. The subclass dispatches `WM_WINDOWPOSCHANGED` to `PersistGeometry`, which synchronously rewrites `Settings::m_window`. If subclass attaches first, WinUI's startup layout pass clobbers the loaded geometry before it can be applied — silent failure where every launch "restores" to the OS-default rect. Caught + fixed (see CLAUDE.md gotcha #6 and the long comment in `ApplyPersistedGeometry`).
- **Tab type discrimination via `try_as<>()`**: tabs come in three flavors today (`VmTabPage`, `WelcomePage`, `AppSettingsPage`), stored in `TabViewItem.Tag()`. Per-tab loops in `MainWindow` (`OnTabSelectionChanged`, `CloseTabItem`, `OnVmManagerChanged`, `PersistOpenTabs`, `RestoreOpenTabs`) discriminate via `item.Tag().try_as<...>()`. No common interface — IDL ceremony isn't worth it for the count we have. Adding a new tab type means extending each of those loops + adding a `OpenXxxTab` factory on MainWindow + a `type` string in the `OpenTab` schema.
- **App Settings is a tab, not a dialog**: short-lived AppSettingsDialog was replaced with AppSettingsPage. Reason: modal disrupts the "change a setting and test it out" loop; a persistent tab lets the user keep it open. Implication: every setting is instant-apply (no Save button); appearance changes that need a full repaint arm a restart banner instead. Welcome tabs can have duplicates (per-host portal model); settings tab is always deduped (singleton surface). Closing settings as the last tab exits the program (same as closing the last welcome tab).
- **Welcome tab = per-host portal** (not "start page"). Tab header is the host's machine name; the Devices glyph marks it as a host. Once remote-host support lands, the `+` button gains a dropdown to spawn local- or remote-host welcome tabs. See [[hyprv-welcome-tab-role]] memory for the rationale.
- **The welcome page also hosts Remote Hosts** (Tier 2 work — see backlog). Not just Hyper-V VMs. Architectural framing: the welcome tab is the user's "where do I go" surface; from one place they pick a local VM, a recently-used VM, OR a saved remote Windows machine to connect into. The same `hyprv-rdphost.exe` machinery drives both — only the parent's `Connect` vs. `ConnectLocalVm` choice differs. Don't design a separate "remote machines" surface; extend this one. Same goes for the rail's `remoteHostsExpander` — it's a second projection of the same saved-hosts list, hidden when empty.
- **Avoid "Remote RDP" as a name.** RDP already means "Remote Desktop Protocol" — "Remote RDP" is redundant. The user-facing surface is "Remote Hosts" everywhere. "RDP" only appears in code identifiers where it disambiguates from Hyper-V (`RdpHostClient`, `RemoteHostTabPage` with an `RdpHostClient` inside it, etc.).
- **Welcome → VM replace-on-open ordering**: `WelcomePage::OpenVm` defers `MainWindow::ReplaceTabWith` to the next dispatcher tick. Synchronous `OpenVmTab` + `CloseTabItem` racing WinUI's deferred `SelectionChanged` dispatch left the new VM tab appended-but-not-selected. The `ReplaceTabWith` helper also force-reselects the new VM tab as a safety net.
- **Tab strip styling**: terminal-y flat (square corners, no fills, dimmed unselected text), 2 DIP accent underline painted via the selected tab's BACKGROUND gradient (zero layout allocation — using `BorderThickness` for the underline allocated a height slot that showed through as a visible seam on unselected tabs). Row 0 height pinned to exactly 32 DIP. Hover backgrounds fill the full button bounds via `CornerRadius=0` overrides (scoped to TabView via `ControlCornerRadius=0` so it doesn't leak globally).
- **VM tab focus on activation**: `RdpHostClient::Focus()` calls `SetFocus(childHwnd)` from hyprv's UI thread; cross-process focus only works after `AttachThreadInput`, which the same call performs idempotently. Without this, switching to a VM tab required an extra click to deliver keystrokes.
- **Default UI density** is **compact** (matches the rail). 12pt body text, ~26 DIP row heights, no decorative headers. See [[hyprv-ui-density]] memory.
- **NIC switch disconnect wire shape**: `HostResource=[]` + `EnabledState=3` (Disabled). Matches `Disconnect-VMNetworkAdapter`'s on-the-wire payload.
- **NIC identification for edits**: each `NetworkAdapter` carries a `nicGuid` extracted from the second GUID in `Msvm_SyntheticEthernetPortSettingData.InstanceID` (format: `Microsoft:<VM-GUID>\<NIC-GUID>`). The allocation row is then found via `WHERE InstanceID LIKE 'Microsoft:<VM-GUID>%<NIC-GUID>%'`.
- **Modal-dialog Z-order vs rdphost popup**: the mstscax popup is a top-level HWND owned by `hyprv-rdphost.exe`, so it paints above the XAML composition surface and eclipses any `ContentDialog` opened over a running VM tab. Fix: refcounted popup suppression via `MainWindow::PushPopupSuppression` / `PopPopupSuppression`, with an RAII `PopupSuppressionScope` declared before every `co_await dlg.ShowAsync()`. `VmTabPage::SetPopupSuppressed` is distinct from `HidePopup` — it leaves `m_wantsVisible` alone so the popup returns to its prior visibility on dialog close without disturbing the active-tab latch. Nested dialogs share one suppression via the refcount.
- **Single dialog-confirmation entry point**: every destructive prompt funnels through `hyprv::app::ui::ConfirmAndAct(weakWindow, actionKey, title, body, primaryText, action)` in `src/app/ui/ConfirmDialog.{h,cpp}`. The helper checks `Settings::ConfirmationEnabled(actionKey)` first and runs `action` immediately (no dialog, no popup suppression) when off. New destructive actions MUST flow through this helper and MUST add their key to the `DefaultConfirmationEnabled` switch in `Settings.cpp` + the `kConfirmEntries` table in `AppSettingsPage.xaml.cpp` at the time of first use. Unknown keys fail safe (return `true`) but won't be user-toggleable until added to those two places.
- **Settings confirmation overrides are sparse**: only keys the user has explicitly toggled persist in `settings.json` (`"confirmations": { ... }`). Missing keys read from `DefaultConfirmationEnabled`. Changing a default later automatically applies to existing installs unless the user has explicitly opted in/out.
- **Backdrop controllers, not built-in backdrop wrappers**: `MicaController` / `DesktopAcrylicController` give us `IsInputActive=true` (Acrylic stays vibrant on deactivation) AND `TintOpacity` access for the user-facing intensity sliders. `MicaBackdrop` / `DesktopAcrylicBackdrop` offer neither — don't go back to them.
- **Black mode = pure-black tint on the active backdrop, NOT a backdrop-off case**: TintColor=RGB(8,8,8), LuminosityOpacity=1.0, controller still active. Stacks with the user's intensity slider so OLED-friendly opaque black is reachable via TintOpacity=1.0.
- **Popup chrome theming requires per-flyout work**: `MenuFlyout`s accept a `SystemBackdrop` (applied via `PopupBackdrop::ApplyTo`). `ContentDialog` and `ComboBox` dropdowns DO NOT in WindowsAppSDK 2.1 — they paint with a theme brush (`ContentDialogBackground` / `ComboBoxDropDownBackground`) that we override in Black mode to keep popups consistent with the window. In Dark and Black modes we also paint a translucent `MenuFlyoutPresenterBackground` overlay so menus don't look like a flat block over Mica.
- **Per-VM `vmPrefs` is sparse**: only VMs the user has explicitly touched persist in `settings.json`. `EnhancedSessionPref` defaults true for unknown VMs; `EnhancedSessionEverSupported` defaults true (benefit of doubt). The "supported" observation is sticky-true — once we've seen a positive, we never write a negative, so a boot-screen "not available right now" snapshot doesn't grey out the toggle for a perfectly capable VM.
- **Enhanced session pref acts as an opt-OUT**: `StartConnection` uses `enhancedSessionAvailable AND userPref`. Pref-on for a guest that can't do enhanced (Linux without LIS) is a no-op, not a broken session.
- **MenuFlyout chrome can't be cleanly narrowed**: WinUI reserves a 28-DIP leading column when any `ToggleMenuFlyoutItem` is present in a menu, AND the toggle template's own `CheckGlyph` column is hardcoded to ~28 DIPs. We tried overriding the theme thicknesses and retemplating the toggle — both broke alignment between toggle and non-toggle items because the placeholder thickness and the column width can't be decoupled without retemplating BOTH `ToggleMenuFlyoutItem` and `MenuFlyoutItem`. Accepted: stock toggle, stock chrome.
- **Closing the last non-VM tab exits the program**: regardless of whether it's a welcome tab or the settings tab. Previously only welcome triggered this; settings stranded the user with an empty window. VM tabs are special-cased (closing the last VM tab opens a welcome tab instead so the user doesn't lose their host portal context).
- **Tab restore opens VM tabs unconditionally, NEVER skips on `GetByGuid==nullopt`**: `MainWindow::OnActivated` runs synchronously on the UI thread, before VMManager's poll thread has done its first WMI snapshot. Every restore-time `GetByGuid` returns null. The old "skip missing VM" branch silently dropped every VM tab, and the final `PersistOpenTabs()` at the end of restore wrote that truncated list back — erasing the user's VM tabs forever on every launch. Now the VM tab opens with an empty display name and `VMManager::HasFirstSnapshot()` gates the placeholder UI between "Loading…" (cold-start, VM not in cache yet) and "(missing VM)" (polled, genuinely gone). Don't reintroduce a cache-existence check during restore.
- **Popup rect must be computed BEFORE `RdpHostClient::Show()`**: the layout pass that gives the `rdpHost` Border its real `ActualWidth/Height` doesn't run synchronously inside `MainWindow::OnTabSelectionChanged` → `VmTabPage::ShowPopup` — Border is still 0×0 when ShowPopup is called for a newly-mounted page. Calling `Show()` before bounds are known surfaces the popup at whatever rect it was last placed at (often the StartConnection fallback `(window_x, window_y+32, 1024x768)` if the rdphost was spawned during cold-start while the tab was unmounted), producing a visible flash before the eventual reposition. Fix is the `m_deferredShow` latch: ShowPopup pins first, Shows only on success; if Border has no size yet, the latch is resolved by `OnLoaded` (first mount) or `OnRdpHostSizeChanged` (re-mount). All four entry points that touch popup visibility (`ShowPopup`, `HidePopup`, `OnLoaded`, `OnRdpHostSizeChanged`, plus `TearDownClient` to clear) share the latch — change one, audit the others.
