- **Graceful Restart via integration services — ✅ resolved, no further work planned.** Shut down uses `Msvm_ShutdownComponent::InitiateShutdown` (`VMManager::ShutdownVM`, force=false) — the VM stays **Running** until the guest OS halts, so Turn off works as a force-off escape hatch throughout (confirmed in the app). **Restart is already a graceful, IS-dependent reboot** via `Msvm_ComputerSystem::RequestStateChange(Reboot=10)` — the same path `Restart-VM` (no `-Force`) takes (`Reset`, the hard reboot, is `RequestStateChange(Reset=11)`). _Correction to the prior note here:_ `Msvm_ShutdownComponent` **does** expose `InitiateReboot(Force, Reason)` — the guest-IS sibling of `InitiateShutdown` (verified against live WMI), so a guest-IS reboot path *does* exist. We're intentionally NOT switching Restart to it: the mid-restart force-off gap is the same shape as Shut down's but matters far less (Restart returns to Running quickly). If we ever want Turn off to work mid-restart, `InitiateReboot` is the drop-in (mirror `VMManager::ShutdownVM`). CLAUDE.md gotcha #22 carries the corrected facts.

  **🔴 P0 — VM-settings correctness pass [user, 2026-05-31] — do before/around the niche items; affects trust.**
  - **Always surface a save failure.** When a VM-settings change is applied and Hyper-V rejects it (a silent no-op of the `ret=4096`/`80070057` family, a state-gate rejection, a bad value), the user must ALWAYS see an error — an InfoBar/banner in the dialog, not a silent swallow. A user who changes a setting, gets no error, and finds it didn't stick "is going to be a bit upset." The dialog HAS an InfoBar for apply errors (`SetNetworkAdapter*` etc. push to an `errors` vector surfaced after the batch), but this needs an audit: every `Set*` path's failure must reach that banner, AND a write that *returns success but silently didn't stick* (the silent-no-op family — gotchas #7/#16/#35) needs a post-write read-back + diff so we can flag "Hyper-V didn't accept this" rather than reporting a false success. Audit all apply paths in `VmSettingsDialog::OnPrimaryButtonClick` + `VMManager::Set*`.
  - **State-gating audit — grey out off-only settings when the VM is running.** Go through EVERY editable setting and determine whether Hyper-V allows changing it while the VM is on; if it can't be changed live, the control must be greyed unless the VM is Off (the affordance IS the error prevention). Several are already gated (memory/processor/firmware/security/SCSI-add → Off; switch/VLAN/DVD-media → live; NIC add/remove → Off-or-running-Gen2). But the set was assembled piecemeal — the **MAC-while-running bug** (shipped fix: MAC is a device property Hyper-V locks while running, now Off-gated) shows the gating wasn't exhaustively verified. Verify each setting reversibly (running vs off) and fix any that are editable-but-would-fail. Pair this with the save-failure surfacing above — together they guarantee a user never makes a change that silently no-ops.
