# hyprv — Hard-won gotchas (full detail)

These are the subtle, expensive-to-rediscover invariants behind hyprv. **This file is the single source of truth for gotchas** — `CLAUDE.md` only points here. Many are also documented inline at the relevant code site and in the user's memory file `hyprv-rdphost-gotchas.md`.

**Discovered a new gotcha? Add it here** — next number, in the matching area section below (and write it up inline at the code site too). Do NOT add gotcha detail to `CLAUDE.md`.

## rdphost / mstscax / IPC

1. **AtlAxWin size = popup size at creation.** Mismatch produces a smaller-than-popup render area with mstscax-painted letterbox. Fixed by querying the popup's client rect at child startup.
2. **mstscax `EnableFrameBufferRedirection` extended property is essential** for VM connections — without it, mstscax renders the credential UI in a fixed-size upper-left rect.
3. **`Msvm_Keyboard` is the right path for Ctrl+Alt+Del and clipboard-paste**, not mstscax.
4. **`SELECT *` in WQL when you need `__PATH`** — explicit column lists drop system properties. Bit us on the snapshot list bug.
5. **rdphost log IPC must wait until after `HwndReady` is sent** + after the parent's rx thread is up. Sending `LogLine` frames inside the parent's synchronous `SpawnAndHandshake` window made the parent's blocking `ReadExact` consume a `LogLine` header as if it were `HwndReady`.

24. **Windows-key passthrough needs `KeyboardHookMode=1` on `IMsRdpClientSecuredSettings` (via `get_SecuredSettings2`).** mstscax's `KeyboardHookMode` defaults to `2` = "apply Windows-key combos (Win, Win+R, Alt+Tab, …) to the remote session ONLY in full-screen mode." Our mstscax host is windowed/embedded (a popup over a XAML Border), so the default lets the HOST swallow Win/Win+R (host Start menu / Run dialog open instead of the guest's). Set it to `1` (always send to the remote session while the control has focus) in `RdpHost::OnConnectLocalVm`. **The property lives on `IMsRdpClientSecuredSettings`, reached via `rdp->get_SecuredSettings2(&sec)` — NOT the base `IMsTscAx::get_SecuredSettings`, which returns the older `IMsTscSecuredSettings` that has no `KeyboardHookMode` (compile error C2664).** It is NOT on AdvancedSettings either (C2039). Set at connect time, so it only takes effect on a fresh connection (reconnect the tab after changing it).

15. **RDP options are parent-prepared, child-applied — both sides must be edited together.** The wire-format `hyprv::ipc::RdpOptions` struct in `src/shared/RdpIpc.h` carries every knob (audio mode, redirection flags, color depth, DPI scale, etc.). `VmTabPage::StartConnection` (parent side) fills it from `Settings::RdpOptionsFor(guid)`. The child side (`RdpHost::OnConnectLocalVm` in `src/rdphost/RdpHost.cpp`) must call the matching `IMsRdpClientAdvancedSettings::put_*` on the mstscax proxy — without that, mstscax never learns about the value and the wire field is silently dropped. We shipped per-VM RDP options once and they did nothing for a session because only `colorDepth` / `desktopWidth` / `desktopHeight` had `put_*` calls; everything else was on the wire but never applied. Mapping: `audioMode` → `put_AudioRedirectionMode(UINT)`; `Flag_RedirectClipboard` → `put_RedirectClipboard(VARIANT_BOOL)`; `Flag_RedirectDrives` → `put_RedirectDrives`; `Flag_RedirectDevices` → `put_RedirectPrinters` (mstscax conflates "devices" with "printers"); `Flag_RedirectPorts` → `put_RedirectPorts`; `Flag_RedirectSmartCards` → `put_RedirectSmartCards`; `Flag_AudioCaptureRedirect` → `adv7->put_AudioCaptureRedirectionMode(VARIANT_BOOL)`. **Adding a new RDP knob requires FOUR coordinated edits — Settings field + JSON load/save, App Settings + VM Settings UI rows, wire mapping in `VmTabPage::StartConnection`, and the `put_*` call in `RdpHost::OnConnectLocalVm`.** Skipping the last one produces a "settings save fine, but nothing happens" bug that's hard to spot because the data flow up to mstscax looks correct. **Display-scale (DPI) override (v13) has an extra wrinkle: it must be applied in TWO parent places.** The connect-time `opts.dpiScalePercent` sets the child's `DesktopScaleFactor`, but for enhanced (fit-to-window) sessions `VmTabPage::UpdateRdphostBounds` then calls `UpdateSessionDisplaySettings(bw, bh, dpi, dpi)` on every resize — and that DPI (which `RdpHostClient` turns into the session's `physWidth`, conveying the effective scale; `desktopScale` is hardcoded 100 there) would snap the guest back to host DPI. So `VmTabPage` caches the user's override in `m_dpiOverridePercent` and uses `override*96/100 ?: GetDpiForWindow` in BOTH `StartConnection` and the resize path. A new scale-ish knob that's only wired at connect will appear to work until the first window resize. (`initialDesktopWidth/Height`, by contrast, only matter for *basic* sessions — enhanced renegotiates them away — so they're surfaced with an "applies to basic sessions" hint and need no resize-path handling.)

49. **`hyprv-rdphost.exe` MUST be manifested `PerMonitorV2` to match the parent — a DPI-awareness MISMATCH across the cross-process popup boundary mis-scales the whole RDP surface on any display set above 100%.** The parent (`src/app/app.manifest`) is `PerMonitorV2`; the child shipped with **no manifest at all → DPI-unaware** (the Win32 default). The parent computes the popup geometry in **physical pixels** (`VmTabPage::ComputeBorderScreenRect`: `topLeft.X * (GetDpiForWindow/96)` + `ClientToScreen` origin) and `SetWindowPos`-es the child's owned top-level popup with those physical coords (`RdpHostClient::EmbedInto` / `Reposition`); it also sends the true monitor DPI as `opts.dpiScalePercent` → the child's `DesktopScaleFactor`. With the child DPI-unaware on, say, a 150% monitor, the OS **bitmap-virtualizes** that window: `GetWindowRect` / `SetWindowPos` / `WM_SIZE` on the child operate in virtualized 96-DPI coordinates while the PMv2 parent feeds it physical ones. The two coordinate spaces diverge, and mstscax (querying the monitor DPI itself, getting 96, contradicting the `DesktopScaleFactor=150` we pushed) renders the session framebuffer small and corner-anchored inside an `AtlAxWin` sized in the other space — the user sees the RDP content shrunk into the upper-left of the black `rdpHost` Border with dead space around it (only visible when the display scale ≠ 100%; at 100% the two spaces coincide so the bug hides). **Fix: `src/rdphost/app.manifest` declares `<dpiAwareness …>PerMonitorV2</dpiAwareness>` and the `.vcxproj` references it via `<Manifest Include="app.manifest" />`** (mirrors the parent's wiring; `mt.exe` merges it into the EXE's `RT_MANIFEST`). Once both processes share PerMonitorV2 there's one physical-pixel coordinate space across the boundary and mstscax reads the real DPI — no parent-side change needed (the parent was already emitting physical pixels + real DPI; it was just talking to a process that interpreted them in a virtualized space). The popup is an *owned top-level* `WS_POPUP` (not `WS_CHILD`), so its DPI awareness is the rdphost process's own — the parent always re-drives geometry via `Reposition`, so no `WM_DPICHANGED` handler is needed in the child. **General rule: any process that hosts a window owned/parented/positioned by hyprv across the process boundary must declare the SAME DPI awareness as the parent (`PerMonitorV2`), or mixed-mode virtualization silently corrupts geometry above 100% scale.** Verify the embedded awareness with `mt.exe -inputresource:<exe>;#1 -out:<tmp>`.
    - **PerMonitorV2 fixes the COORDINATE space but exposed two guest-SCALE follow-ups (both confirmed):** (1) **Enhanced post-login scale.** `RdpHostClient::UpdateSessionDisplaySettings` hardcoded `desktopScale = 100` — harmless when the child was DPI-unaware (its framebuffer was virtualized), but with PerMonitorV2 + physical-pixel `w/h` the guest then laid its UI out at 100% on a physical-res desktop → everything tiny inside the VM. Now it derives the host scale % from the DPI the parent passes and snaps to an RDP-valid `desktopScaleFactor` via `SnapRdpScalePercent` → one of {100,125,150,175,200,250,300,400,500} (mstscax returns `E_INVALIDARG` for any other value, silently leaving the guest at its current scale). (2) **Enhanced PRE-login centering.** The guest centers the logon UI in its LOGICAL desktop = framebuffer px ÷ scale. The connect used a fixed 1024×768 framebuffer, so at 150% the logical desktop was a cramped ≈682×512 and Windows' logon UI drifted toward a corner (at 100% the 1024×768 logical size centers fine — which is why it only showed above 100%). Fix in `VmTabPage::StartConnection`: for enhanced, scale the INITIAL framebuffer by the host scale (1024×768 → 1536×1152 at 150%) so the LOGICAL size stays a constant 1024×768 at any display scale → the logon centers identically to 100%. Capped to the measured Border (SmartSizing is off ⇒ a larger-than-control framebuffer would clip the logon UI); transient (resized to fill the window post-login via `UpdateSessionDisplaySettings`); **enhanced only**. **BASIC (non-enhanced) sessions can't be scaled this way** — a basic Hyper-V console renders at the guest's own native video resolution and honors no RDP scale factor, so mstscax shows it 1:1 (sharp but small on a high-DPI host). A `SmartSizing`-scaled basic popup was tried and reverted [user] — it letterboxed the guest, worse than native 1:1; raise the guest's own resolution instead.

## Window / tab / popup lifecycle

6. **`ApplyPersistedGeometry` must run before `AttachWindowSubclass`** in `OnActivated`. The subclass dispatches `WM_WINDOWPOSCHANGED` to `PersistGeometry`, which synchronously rewrites `Settings::m_window`. If the subclass attaches first, WinUI's initial layout pass fires `WM_WINDOWPOSCHANGED` for the OS-default rect and clobbers the loaded values before they can be applied. Window then "fails to restore" on every launch. See the long comment in `ApplyPersistedGeometry`.

13. **Tab restore can't synchronously call `VMManager::GetByGuid` during `OnActivated`.** Caught this one in production. `RestoreOpenTabs` previously did `GetByGuid(vm.identifier)` to fetch the display name for each persisted VM tab. But `OnActivated` runs synchronously on the UI thread, BEFORE VMManager's poll thread has had a chance to do its first WMI snapshot. Every lookup returned `nullopt`, every VM tab got silently skipped, AND the final `PersistOpenTabs()` at the end of `RestoreOpenTabs` then wrote that truncated list back to `settings.json` — erasing the user's VM tabs forever, on every launch. Fix: restore VM tabs unconditionally with an empty display name; `VmTabPage::UpdateVmTabHeader` resolves it on the first VMManager tick. The new `VMManager::HasFirstSnapshot()` accessor lets `VmTabPage::UpdatePlaceholderAndClient` distinguish "cold-start, VM not yet in cache" (show centered loading overlay) from "VMManager has polled, VM is genuinely gone" (show "(missing VM)" placeholder). Don't gate tab restore on a cache that doesn't exist yet, AND don't persist the restore's own output.

14. **Cold-start popup-position race in `VmTabPage::ShowPopup`.** When `MainWindow::OnTabSelectionChanged` mounts a previously-unmounted VM page in `tabContentHost` and synchronously calls `ShowPopup`, WinUI's layout pass that gives the `rdpHost` Border its real `ActualWidth/Height` hasn't run yet in the same call stack. `ComputeBorderScreenRect` returns false; `UpdateRdphostBounds` bails. If `Show()` is called before that point, the popup becomes visible at whatever rect it last sat at — typically the StartConnection fallback `(window_x, window_y+32, 1024x768)` if the rdphost was spawned by VMManager's first poll while the tab was unmounted (cold-start restore). The user sees a flash in the top-left corner before the popup repositions. Fix: `ShowPopup` pins FIRST and only `Show`s on success; otherwise latches `m_deferredShow=true` and leaves the popup hidden. `OnLoaded` (first-mount, after first layout pass) and `OnRdpHostSizeChanged` (subsequent-mount, when Border goes 0 → real) both resolve the deferred latch: `UpdateRdphostBounds` + `Show` + `Focus` + clear flag. `HidePopup` / `TearDownClient` also clear the flag so a stale latch can't surface a popup behind the user's back if they navigate away mid-defer. **Touching `ShowPopup` requires also touching `OnLoaded`, `OnRdpHostSizeChanged`, `HidePopup`, and `TearDownClient` — they share the latch.**

## Coroutine / WinUI dialog lifetime

10. **WinUI 3 ContentDialog button-click coroutine gotchas.** When `OnPrimaryButtonClick` is a `fire_and_forget`, the `args` parameter (declared `const&` to match the delegate signature) is a reference to a caller-owned stack value that's gone after the first `co_await`. Calling `args.Cancel(true)` post-suspend AVs trying to dereference a freed COM proxy. Fix: copy into the coroutine frame (`auto args = argsRef;`) BEFORE any await. Also: `winrt::resume_foreground` has no overload for `Microsoft::UI::Dispatching::DispatcherQueue` — only the older `Windows::System::DispatcherQueue`. Use the inline `ResumeOnDispatcher` awaiter in `VmSettingsDialog.xaml.cpp` (or copy it where needed).

19. **An immediately-invoked *capturing lambda coroutine* dangles its captures after the first `co_await`.** `ConfirmAndAct` used to launch its dialog as `[captures]() -> winrt::fire_and_forget { ...; co_await dlg.ShowAsync(); action(); }();`. The captures (`action`, `winStrong`, …) live in the lambda *temporary*, which is destroyed at the end of the full-expression — i.e. the instant the coroutine first suspends at `co_await`. When the dialog closed and the coroutine resumed, `action` was a freed `std::function`; calling it AV'd at a non-executable address (windbg: `std::_Func_class<void>::operator()` → BEX64 / `SOFTWARE_NX_FAULT`). This bit **every confirmation-ON destructive action** (Turn off / Reset / Restart / Shut down / Delete VM / snapshot apply+delete) — it just surfaced reliably on Turn off because the surrounding popup-suppression churn reused the freed closure memory. **Fix: a coroutine that suspends must take everything it needs as by-value PARAMETERS** (those are copied into the coroutine frame and survive the await), never lambda captures. `ConfirmAndAct` now forwards to a file-local `ShowConfirmCoro(win, root, theme, title, body, primary, action)`. Sibling of gotcha #10 (the `args` ref-dangle). The same anti-pattern still exists in `VmTileFactory`'s "Settings…" launcher but is safe-by-accident (nothing reads its captures after the await, and the MainWindow it points to is effectively immortal) — harden it if you touch it.

25. **Show a "working" overlay BEFORE UI-thread-bound WMI work, via `resume_after`, not a single `resume_background` round-trip.** WMI proxies are STA-bound (gotcha #8), so the settings dialog's Save runs its WMI batch on the UI thread — which freezes the UI. To get the "Saving…" overlay painted first, `OnPrimaryButtonClick` sets it visible then `co_await winrt::resume_after(150ms)` (a thread-pool timer — the UI is free to render meanwhile) before `ResumeOnDispatcher` hops back to do the WMI. A single `co_await resume_background(); co_await ResumeOnDispatcher` yields only one cycle, which was enough for fast Sets but NOT once storage edits (create/attach with their settle+poll) hold the UI for a second or two — the spinner appeared late. The overlay still doesn't *animate* during the block (UI thread is held); animating through it would need the WMI work chunked across thread hops.

## Theme / menu chrome

11. **MenuFlyout chrome can't be cleanly narrowed.** WinUI reserves a 28-DIP leading column on every item in a menu the moment any `ToggleMenuFlyoutItem` is present (driven by the `MenuFlyoutItemPlaceholderThemeThickness` theme resource), AND the toggle's own template hard-codes `CheckGlyph Margin="0,0,16,0"` for an additional ~28-DIP check column. Both were investigated this round: overriding the theme thicknesses to smaller values misaligned non-toggle items vs. the toggle's icon (the placeholder margin is shared between "shift past check column" and "shift past icon" semantics, can't be reduced for one without breaking the other), and retemplating the toggle to shrink the check glyph margin still left a visual offset because the column width is auto-sized to glyph content. The current accepted answer is **stock toggle, stock chrome** — every item gets the extra ~28 DIPs of leading space whenever a toggle is in the menu. Don't re-attempt without retemplating BOTH `MenuFlyoutItem` and `ToggleMenuFlyoutItem` end-to-end.

12. **Backdrop controllers (not built-in `*Backdrop` wrappers) for Mica/Acrylic.** `MicaBackdrop` / `DesktopAcrylicBackdrop` don't expose `IsInputActive` (Acrylic falls back to a solid fill on window deactivation) and don't surface `TintOpacity` (no live intensity slider). `MainWindow::ApplyAppearance` manages `MicaController` / `DesktopAcrylicController` directly, plus a `SystemBackdropConfiguration` with `IsInputActive(true)` pinned. Tearing down + re-creating on every appearance change is the simple path; `UpdateBackdropTintOpacity` is the fast path for slider drags (sets `TintOpacity` on the existing controller, no rebuild). Black mode is `TintColor=RGB(8,8,8) + LuminosityOpacity=1.0` on the active controller, NOT a backdrop-off case — `SystemBackdrop(nullptr)` was tried and looked broken in every theme. `ContentDialog` and `ComboBox` dropdowns don't expose `SystemBackdrop` in WindowsAppSDK 2.1 at all — they get opaque near-black brush overrides in Black mode (`ContentDialogBackground` / `ComboBoxDropDownBackground`) via `Application.Current.Resources.Insert`. `MenuFlyout`s DO take a backdrop; apply it per-flyout via `hyprv::app::ui::PopupBackdrop::ApplyTo`. In Dark + Black modes we also paint a translucent `MenuFlyoutPresenterBackground` overlay (alpha 0xA0 on dark/black tint) so menus read consistent with the window's tint while letting the backdrop bleed through.

20. **Rail context-menu state-gating freezes unless re-evaluated in `menu.Opening`.** `MainWindow::RenderRail` reuses existing rail tiles via `UpdateRailItem` (it diffs by GUID, updating the dot/text) and only builds a fresh `ContextFlyout` for *brand-new* tiles. So a tile's right-click menu is frozen at the VM state that existed when the tile was first created — start a VM after its tile was built and the menu still shows Off-state gating (Start enabled, Shut down/Turn off greyed, Delete enabled). The earlier code wrongly assumed "the rail rebuilds every poll." Fix: `BuildVmContextMenu` re-evaluates the `IsEnabled` of every state-gated item (Start/Pause/Save/Restart/Shut down/Reset/Turn off/Delete/Launch debugger/Take snapshot/Revert) from a fresh `GetByGuid` snapshot inside the `menu.Opening` hook — `addItem` returns the `MenuFlyoutItem` so each can be captured as a `weak_ref`. Re-evaluating on open (vs. rebuilding the flyout per poll) is what avoids closing a menu the user has open. The toggle + send-keys items already rode this hook; the Power/snapshot items were the gap.

## WMI fundamentals

7. **Hyper-V `Modify{System,Resource}Settings` wants WMI DTD 2.0 XML, not MOF.** Use `WmiObject::GetCimXml()` which wraps `IWbemObjectTextSrc::GetText(..., 2, ...)`. MOF text (even with `WBEM_FLAG_NONSYSTEM_ONLY`) returns CIM 32773 "InvalidParameter". The XML output keeps system properties (`__PATH`/`__CLASS`/`__NAMESPACE`) and qualifiers — that's what `Set-VMProcessor` sends on the wire, verified by capturing PowerShell's wire format. Do not regex-strip them. Also note: gate edits on `VmState::Off` strictly — Hyper-V silently rejects processor/memory modifies on `Saved` VMs (job completes with no error, no change applied).

8. **WMI proxies are apartment-bound.** `VMManager::m_scope` is built on the UI STA; calling its `IWbemServices` methods from a thread-pool MTA thread returns `RPC_E_WRONG_THREAD` (0x8001010E). Same reason `VMManager::PollLoop` builds its OWN scope on the polling thread instead of borrowing `m_scope`. When you need to do WMI from a coroutine, run the actual `Set*` calls on the UI thread and only put pure-CPU/sleep waits (e.g. `KickPollAndWait`) on the bg thread.

9. **`WmiObject::GetObjectArray` is defensive** — checks `SafeArrayGetVartype` and bails on non-object arrays. Hyper-V declares `ResultingResourceSettings` as `Instance[]` in the MOF but actually returns `VT_BSTR` (embedded-instance XML strings). The pre-fix code dereferenced each BSTR as `IUnknown*` and crashed in `QueryInterface`. Generated `Modify*Settings` wrappers still call `GetObjectArray` for these out-params; the defensive check makes it a no-op instead of an AV.

33. **A single-object CIM `Reference` in-param must be set as the object's `__PATH` string (`.Path()`), NOT the embedded `WmiObject` — and the codegen gets this wrong, so the typed wrappers silently fail.** `WmiObject::Set(name, WmiObject const&)` marshals `VT_UNKNOWN` (an embedded object). That's correct for an *embedded-instance* param but WRONG for a `Reference` param, which wants the object path as a `VT_BSTR` — passing the embedded object returns **`WBEM_E_TYPE_MISMATCH` (0x80041005)** at `IWbemClassObject::Put` time (logged as `"Put failed for <ParamName>"`). The generator emits `in.Set(name, WmiObject)` for ALL single-object params regardless of whether the MOF declares them `REF` or embedded, so **every generated wrapper whose in-param is a single Reference is silently broken.** This is exactly why **snapshots never worked**: `Msvm_VirtualSystemSnapshotService::{CreateSnapshot(AffectedSystem), ApplySnapshot(Snapshot), DestroySnapshot(AffectedSnapshot), DestroySnapshotTree(SnapshotSettingData)}` and `Msvm_VirtualSystemManagementService::DestroySystem(AffectedSystem)` all take **`Reference`** in-params (confirmed via `(Get-CimClass ...).CimClassMethods[m].Parameters[p].CimType == Reference`), and both the typed wrappers and a first manual-invoke cut set them as embedded → `Put failed for AffectedSystem (hr=0x80041005)`. Fix: invoke manually and pass `obj.Path()` for the REF param (`VMManager::{TakeSnapshot,ApplySnapshot,DeleteSnapshot,DestroyVM}`). This is the **single-object** sibling of the REF-array case (gotcha #28's `AddFeatureSettings.AffectedConfiguration` / `AddResourceSettings` REF-param rule, and `WmiObject::SetReferenceArray` for `REF[]`). **General rule: any `Add*`/`Modify*`/`Destroy*`/`Apply*`/`Create*` method param that references an EXISTING object (the thing you operate ON) is a `Reference` → set it via `.Path()`; only the *new/changed settings* params are embedded-instance strings (CIM XML).** When a generated wrapper's call returns `0x80041005` / `"Put failed for <objectParam>"`, this is the cause — bypass the wrapper and `.Path()` the REF. (To regenerate correctly, `gen-hyperv-h.ps1` would need to emit `.Path()` for `Reference`-typed scalar in-params; until then, manual-invoke these.)

**The silent-no-op family (gotchas #7, #16, #17, #26, #30).** A `Modify*Settings`/`Add*Settings` that returns `4096` + a clean `Msvm_ConcreteJob` (`JobState=7`, `ErrorCode=0`) but doesn't stick means Hyper-V silently rejected a property value — wrong format (gotcha #16 braces), or a state gate (Saved/running). There is no error to grep for; compare your serialized XML against what the equivalent PowerShell cmdlet sends on the wire.

## Power / state-change

22. **`Msvm_ComputerSystem::RequestStateChange(Disabled)` is rejected with 32775 while the VM is transitional.** Our Shut down / Restart / Turn off all go through `RequestStateChange`. A graceful Shut down via `RequestStateChange(4)` drives the VM into the `Stopping` state, and a follow-up `RequestStateChange(3)` (force-off) returns **32775 ("invalid state for this operation")** — so you cannot force-off a shutdown-in-progress through this path, and the Turn off menu item is therefore gated to Running/Paused only (enabling it mid-transition surfaces a button that silently fails). Hyper-V Manager can force-off mid-shutdown because its graceful shutdown uses `Msvm_ShutdownComponent::InitiateShutdown` (guest-driven), which keeps the VM **Running** until the OS halts — Turn off (valid while Running) then works throughout. **Shut down now does exactly this** — `VMManager::ShutdownVM` finds the VM's `Msvm_ShutdownComponent` (`WHERE SystemName='<guid>'`) and invokes `InitiateShutdown(Force=false, Reason)` manually (no generated wrapper). So the VM stays Running through the shutdown and Turn off is the working escape hatch. Requires integration services up (no `Msvm_ShutdownComponent` otherwise → no-op + log). **Restart is on `RequestStateChange(Reboot=10)`** — the standard graceful, IS-dependent reboot (the same path `Restart-VM` without `-Force` takes; `Reset` (hard) is `RequestStateChange(Reset=11)`). Correction to an earlier note here: `Msvm_ShutdownComponent` **does** expose `InitiateReboot(Force, Reason)` — the exact guest-IS sibling of the `InitiateShutdown` above (verified against live WMI). We deliberately leave Restart on `RequestStateChange(Reboot=10)` rather than switch it to `InitiateReboot`: the same mid-transition force-off gap exists (a graceful restart briefly drives the VM through a Stopping-like phase where Turn off would 32775), but Restart returns to Running quickly so the gap matters far less than it did for Shut down. If we ever want Turn off to work mid-restart too, `InitiateReboot` is the drop-in (mirror `VMManager::ShutdownVM`).

29. **`KickPollAndWait` waits for a poll cycle that BEGAN AFTER the call — not just any `m_pollGen` advance — so a just-saved setting is in the cache before the dialog reopens.** The settings dialog's Save runs its WMI `Set*`s then `KickPollAndWait(15000)` so a reopen reflects the new values. The original impl waited for `m_pollGen` to merely *change*, which was racy: a poll cycle already in-flight when the edit kicked (it read WMI *before* the `Set` landed) would finish first and bump the gen, satisfying the wait with **pre-edit** data — the dialog reopened stale and only a *second* reopen (after the next cycle) showed the change. Symptom the user hit: "I change a setting, reopen, it's not reflected until I close and reopen again," even though PowerShell shows it changed immediately (raw WMI is fresh; the cmdlet's own read lags, but hyprv's poll uses raw `IWbemServices` queries which ARE fresh). Fix: a request/serviced handshake — `KickPollAndWait` does `req = ++m_pollReq`; `PollLoop` snapshots `m_pollReq` at each cycle's **start** (after consuming the kick) and publishes it to `m_pollServiced` at the cycle **end**; the wait completes only when `m_pollServiced >= req`, which can only be a cycle that started after the request. This is the **systematic** fix — it makes *every* cache-backed field fresh on reopen, so per-page LIVE re-reads (security in gotcha #27, boot order/DVD/disks) are now belt-and-suspenders rather than load-bearing. When adding a new `Set*`/edit path, just call `KickPoll()` on success (and the dialog's batch ends with `KickPollAndWait`); no per-field freshness handling needed.

## Firmware / boot order / secure boot

16. **`Msvm_VirtualSystemSettingData.SecureBootTemplateId` must be written as a BARE GUID (no braces).** Hyper-V stores the template as `1734c6e8-3154-4dda-ba5f-a874cc483422` (no `{}`). If you write the braced form `{1734c6e8-…}` in a `ModifySystemSettings` modify, the call becomes a **silent no-op**: it returns `4096` with an `Msvm_ConcreteJob` that completes "successfully" (`JobState=7`, `ErrorCode=0`) but applies *nothing* — so `SecureBootEnabled` never actually toggles, and `WaitForJob` reports success. There is no error anywhere to grep for; the only symptom is "the toggle saves but the VM's Secure Boot state doesn't change." Casing is irrelevant (Hyper-V compares the GUID case-insensitively); **only the braces break it.** Verified by capturing the working .NET `ManagementObject` call (braced → `ret=4096`, stays Off; bare → `ret=0` synchronous, flips On). `VMManager::SetSecureBoot` strips `{}`/whitespace before calling `vssd.SecureBootTemplateId(...)`. The dialog's well-known template constants (`kSecureBootTemplates[]` in `VmSettingsDialog.xaml.cpp`) keep the braced display form; the read-side `NormalizeGuid` comparison strips braces on both sides, so the bare-vs-braced split only matters at the WMI **write** boundary. **General rule for this class of bug: a `ModifySystemSettings`/`ModifyResourceSettings` that returns 4096 + a clean job but doesn't stick means Hyper-V silently rejected a property value (wrong format, or a state gate like Saved/running) — compare your serialized XML against what PowerShell sends on the wire.**

17. **Gen 2 boot order: write `BootSourceOrder` refs verbatim, and they regenerate after a reorder.** `Msvm_VirtualSystemSettingData.BootSourceOrder` is a `string[]` of WMI reference paths to `Msvm_BootSourceSettingData`. To reorder, **permute the exact ref strings you read and write them back** via `ModifySystemSettings` — do NOT reconstruct them (Hyper-V matches by reference; a reconstructed/mismatched string silently no-ops, same failure shape as gotcha #16). After a successful reorder, the boot-source references **regenerate** (new `InstanceID`s), so a ref captured before one write is stale for the next. `VMManager::GetBootOrder` resolves each ref to its `BootSourceDescription` for a label; `SetBootOrder` writes the permuted refs. The settings dialog's read-fresh-on-open / write-once-at-Save flow sidesteps the staleness; any multi-write flow must re-`GetBootOrder` between writes. **Gen 1 BIOS boot order (v12)** uses a different mechanism: `Msvm_VirtualSystemSettingData.BootOrder`, a **`uint16[]` of device-type codes** (`0`=Floppy, `1`=CD/DVD, `2`=Hard Drive (IDE), `3`=Legacy Network Adapter — verified: WIN7X64 reads `1,2,3,0`). `VMManager::GetBootOrderGen1` maps codes→labels; `SetBootOrderGen1` permutes the codes and writes via `ModifySystemSettings`. This was the long-standing "generated setter is a no-op stub" blocker — now fixed: `WmiObject::SetUInt16Array` (a `VT_ARRAY|VT_I4` SAFEARRAY — WMI carries CIM uint16 arrays as VT_I4, which the `BootOrder` *getter* already confirms by narrowing from `GetUInt32Array`), the generated `BootOrder` setter routes through it, and `gen-hyperv-h.ps1` now emits `SetUInt16Array` for `UInt16Array`/`SInt16Array` so a regen won't re-stub it. **Gen 1 boot order needs the VM Off** — the modify silently no-ops on Saved/running (`ret=4096`, clean job, nothing applied; verified — the same silent-no-op family as #7/#16/#26). The dialog shows the Firmware nav item for both gens (relabeled "BIOS" for Gen 1, Secure Boot subsection collapsed); boot-order edit is gated to Off, Secure Boot to Gen 2 + Off.

## Storage (controllers / disks / DVD)

18. **DVD mount/eject: an empty drive has no media object — mount=Add, change=Modify, eject=Remove.** A Hyper-V DVD *drive* is a `Msvm_ResourceAllocationSettingData` (ResourceType 16, "Synthetic DVD Drive", both Gen 1 and Gen 2). The *disc* is a SEPARATE `Msvm_StorageAllocationSettingData` ("Virtual CD/DVD Disk", ResourceType 31) whose `HostResource[0]` is the ISO path — and it exists ONLY while a disc is mounted. So: **mount** (empty→ISO) = clone the default media template + set `Parent`(drive `__PATH`)+`HostResource`(ISO) + `AddResourceSettings`; **change** (ISO→ISO) = `ModifyResourceSettings` on the media object; **eject** (ISO→empty) = `RemoveResourceSettings` on the media object. Clearing `HostResource` via `ModifyResourceSettings` does NOT eject — Hyper-V rejects it (`ret=4096`, job state 10/Exception, `CIM 32773`). The default media template is found by `SELECT * FROM Msvm_StorageAllocationSettingData WHERE ResourceSubType='Microsoft:Hyper-V:Virtual CD/DVD Disk'` and picking the row whose InstanceID contains `Definition` (mounted media carry the VM GUID instead). `AddResourceSettings` AffectedConfiguration is the realised VSSD `__PATH` (a REF passed as a path string). **`RemoveResourceSettings` (and all `Remove*ResourceSettings`/`Remove*FeatureSettings`) generated wrappers are still no-op stubs** (the ReferenceArray in-param TODO); invoke them manually — `SpawnMethodIn` + `WmiObject::SetReferenceArray(L"ResourceSettings", {mediaPath})` + `InvokeMethod` — see `VMManager::SetDvdMedia`. All of this was verified against live WMI before coding (`Set-VMDvdDrive` mount→eject removes the SASD; clearing HostResource errors). DVD media hot-swaps, so none of it needs the VM Off. **Adding/removing the DVD *drive* itself (v11)**: a DVD drive is the same RASD shape as a disk drive (gotcha #23's drive-add step) — `VMManager::AddDvdDrive` picks the first SCSI (Gen 2) / IDE (Gen 1) controller + next free `AddressOnParent` slot (shared with disk drives), clones the default "Synthetic DVD Drive" template (`ResourceSubType='Microsoft:Hyper-V:Synthetic DVD Drive'` + `InstanceID LIKE 'Microsoft:Definition%Default'`), and `AddResourceSettings` — ONE layer (no media). `RemoveDvdDrive` removes the media SASD first (if a disc is mounted) then the drive RASD, mirroring `DetachVhd`. Verified `ret=0` raw on Off + hot add/remove on a running Gen 2 VM; gated `isOff || (m_isGen2 && Running)` like NIC add/remove (gotcha #28).

23. **Attaching a VHD is two layered AddResourceSettings, and the new drive's path must be re-queried.** A hard disk is `controller → disk-drive RASD → VHD SASD`: the controller is a `Msvm_ResourceAllocationSettingData` (SCSI = ResourceType 6, IDE = 5), the disk drive is a child RASD (ResourceType 17, "Synthetic Disk Drive") with `AddressOnParent`=slot + `Parent`=controller, and the VHD is a `Msvm_StorageAllocationSettingData` ("Virtual Hard Disk") with `HostResource`=vhdx + `Parent`=the disk drive. `VMManager::AttachVhd` therefore: (1) clones the default disk-drive template (`InstanceID` ends with `\Default`, subtype "Synthetic Disk Drive" — there's also a "Physical Disk Drive" template + `\Minimum`/`\Maximum`/`\Increment` variants to skip), sets Parent+AddressOnParent, `AddResourceSettings`; (2) **re-queries** the new drive by (controller, slot) because `AddResourceSettings`' `ResultingResourceSettings` comes back as embedded XML, not a usable object (gotcha #9); (3) clones the default VHD template, sets Parent=new drive + HostResource=vhdx, `AddResourceSettings`. Detach removes the VHD SASD then the disk-drive RASD (manual `RemoveResourceSettings` via `SetReferenceArray`). `AddressOnParent` is a CIM **string**. SCSI hot-add works on a running VM; IDE (Gen 1) generally needs the VM Off. `AffectedConfiguration` is the realised VSSD `__PATH`. **The add-VHD step is eventually consistent: when it returns 4096 (async) right after the drive add, the VHD often doesn't link immediately** (drive present, VHD absent — an orphan empty drive). `AttachVhd` handles this by settling ~1 s, re-resolving the drive ref (it can regenerate after a modify), adding the VHD, then POLLING ~3 s for the link to appear; if it never links it rolls the orphan disk drive back so no empty drive is left behind. **Creating a new VHD**: `VMManager::CreateAndAttachVhd` spawns a `Msvm_VirtualHardDiskSettingData` (Type 3=dynamic/2=fixed, Format 3=VHDX, Path, MaxInternalSize) via `WmiScope::GetClass` + raw `SpawnInstance`, invokes `Msvm_ImageManagementService::CreateVirtualHardDisk` (manual — no generated wrapper), then `AttachVhd`s the file.

30. **A SCSI controller has no intrinsic index (number it by enumeration order); adding one is Off-only.** The storage destination picker (`VMManager::GetStorageControllers`) lets the user choose which controller + slot a new disk/DVD lands on. Facts, each verified reversibly against live WMI before coding:
    - **SCSI controllers carry no number.** A 2nd `Msvm_ResourceAllocationSettingData` ResourceType=6 ("Synthetic SCSI Controller") added to a VM comes back with an **empty `Address`** and an **identical `ElementName`** ("SCSI Controller") to the first — Hyper-V Manager's "SCSI Controller 0/1/2/3" is purely **enumeration order**. So we number SCSI controllers by stable InstanceID sort. **IDE controllers DO carry `Address` (0/1)** — use that as the number. `GetStorageControllers` lists IDE first (HVM order) then SCSI, and `GetHardDisks` resolves each disk's controller label through the same map so the disk cards and the picker read identically.
    - **Adding a SCSI controller is rejected while the VM is Running** — `AddResourceSettings` of the default "Synthetic SCSI Controller" template returns a job that fails with state 10 / err **32770** *"cannot add device 'Synthetic SCSI Controller' while the virtual machine is running."* (Disk/DVD *drives* hot-add on a running Gen 2 VM — gotchas #18/#23 — but the *controller* itself does not.) So `VMManager::AddScsiController` is gated to **Off** and capped at 4 SCSI controllers/VM. On Off it's synchronous (`ret=0`), so the dialog applies it **immediately** (not Save-batched) and re-reads `GetStorageControllers` (raw WMI is fresh) to surface the new controller for subsequent attach/create — the one storage op that bypasses the snapshot/diff model (a bare controller is harmless + removable, and queued ops need a real ref to target).
    - **`AttachVhd`/`CreateAndAttachVhd`/`AddDvdDrive` gained optional `controllerRef`+`slot`** (empty/-1 preserves the old auto-pick: SCSI preferred, lowest free slot). The shared `ResolveStorageTarget` helper honors an explicit ref+slot or auto-picks. The slot combos offer free slots minus VM-used minus **already-queued-this-session** (`m_queuedSlots`), so two queued ops never collide on one slot. Controller `__PATH`s are InstanceID-stable across child adds, so a ref captured at dialog-open is still valid at Save (unlike the *drive* refs of gotchas #17/#23, which regenerate).
    - **`RemoveScsiController` = `RemoveResourceSettings` on the controller RASD, gated to EMPTY controllers only.** The dialog only enables Remove for a SCSI controller with no VM-side device AND no queued device (detach/cancel first), so it's the exact reverse of the add (`ret=0` on Off). Off-only, like the add. IDE controllers are fixed hardware — no remove. **Removing a *middle* SCSI controller renumbers the higher ones** (SCSI numbering is enumeration order), so after an immediate add/remove the dialog calls `RebuildStorageCards()` to re-read + rebuild the controller/disk/DVD cards (it deliberately does NOT touch the queued-op state, so queued attaches survive a controller add/remove).
    - **UI shape (settled after a first cut the user rejected):** a first attempt used a standalone "New device on" controller+slot picker at the top — confusing. The shipped design is **controller-centric**: a Controllers subsection (numbered label + device count + per-SCSI Remove + Add SCSI controller) and **per-device placement flyouts** (Attach/Create/Add-DVD each pick controller+slot in-context, combos repopulated on `Opening`). Every disk/DVD card shows "SCSI Controller N · Slot M". Add/Remove controller apply immediately (not Save-batched) so the placement flyouts always see real controllers.

## Network adapters

21. **A "dynamic" NIC MAC is an EMPTY `Address`, not zeros.** `Msvm_SyntheticEthernetPortSettingData` carries `Address` (the 12-hex MAC) + `StaticMacAddress` (a *bool*: true=static override, false=Hyper-V-assigned). To set static: `Address=<12 hex>` + `StaticMacAddress=true`. To revert to dynamic: `StaticMacAddress=false` **and `Address=""` (empty)** — Hyper-V then assigns from the host pool (`Msvm_VirtualSystemManagementServiceSettingData.{Minimum,Maximum}MacAddress`). The `Set-VMNetworkAdapter -DynamicMacAddress` cmdlet itself is buggy here — it writes all-zeros and Hyper-V rejects it ("Dynamic MAC address 00-00-00-00-00-00 … is invalid"); existing dynamic NICs verifiably carry an *empty* Address. `VMManager::SetNetworkAdapterMac` writes the empty-Address form via `ModifyResourceSettings`.

28. **Adding a NIC is TWO `AddResourceSettings` (port + connection); the access VLAN is a feature setting on the *connection*.** A synthetic NIC layers as `Msvm_SyntheticEthernetPortSettingData` (the adapter, InstanceID `Microsoft:<VM-GUID>\<NIC-GUID>`) → `Msvm_EthernetPortAllocationSettingData` (the switch connection, InstanceID `…\<NIC-GUID>\C`, `Parent`=port, `HostResource`=switch path). Each fact below was verified against live WMI before coding (reversible add→inspect→remove + VLAN set→read→untag on a stopped VM, replicating the exact `AddResourceSettings`/`RemoveResourceSettings`/`Add`/`RemoveFeatureSettings` calls the C++ makes):
    - **A raw `AddResourceSettings` of just the synthetic port does NOT auto-create the Ethernet Connection allocation** — only `Add-VMNetworkAdapter` (the cmdlet) adds both. So `VMManager::AddNetworkAdapter` does two layered adds: clone the default "Synthetic Ethernet Port" template (`InstanceID LIKE 'Microsoft:Definition%Default'`), set `ElementName` + **one** fresh braced `VirtualSystemIdentifiers` GUID (Hyper-V appends a second itself and assigns the MAC from the pool — don't set Address), `AddResourceSettings`; then re-query the new port **by the VSI GUID** (its `ResultingResourceSettings` is embedded XML — gotcha #9), clone the default "Ethernet Connection" template, set `Parent`=new port + `HostResource`/`EnabledState` (`[switchPath]`+`2` connected, `[]`+`3` disconnected — the disconnected shape matches gotcha #21's `SetNetworkAdapterSwitch` disconnect), `AddResourceSettings`. **If you skip the connection add, the NIC exists but `SetNetworkAdapterSwitch` later fails "allocation not found"** (it modifies the allocation, never creates one).
    - **Remove = `RemoveResourceSettings` on the allocation (child) THEN the port (parent)**, manual `SpawnMethodIn`/`SetReferenceArray`/`InvokeMethod` (generated wrapper is a stub). Child-first is unconditionally safe regardless of whether removing the port would cascade. Mirrors `DetachVhd`.
    - **VLAN = `Msvm_EthernetSwitchPortVlanSettingData`, a *feature* setting on the Ethernet Connection allocation** (NOT the port). `OperationMode` is UInt32 `1`=Access / `2`=Trunk / `3`=Private; `AccessVlanId` UInt16. Set: existing setting → `ModifyFeatureSettings`; none → clone the default VLAN template (`…Definition%Default`) + `AddFeatureSettings`. **`AddFeatureSettings.AffectedConfiguration` is a REF — pass the allocation `__PATH` string** (invoke manually like `AddResourceSettings`; the *generated* `AddFeatureSettings` wrapper marshals it as an embedded instance via `Set(WmiObject)`, which is wrong for a reference param — same reason all the `AddResourceSettings` call sites invoke manually). Untag → manual `RemoveFeatureSettings` (ReferenceArray, also a stub). The VLAN setting's InstanceID embeds `<VM-GUID>\<NIC-GUID>\C\…`, so the per-poll read parses both GUIDs out of it; only `OperationMode==1` (Access) is surfaced as `NetworkAdapter::vlanId`, trunk/private read as 0 to match the access-only dialog UI.
    - **`Get-VMNetworkAdapterVlan` read-back lags ~1 s after a `RemoveFeatureSettings`** (the cmdlet's cached view) — a raw `Msvm_EthernetSwitchPortVlanSettingData` query is authoritative and showed the untag took effect immediately. Don't trust a same-pipeline cmdlet read to confirm a raw-WMI mutation.
    - **State gate:** Add/Remove NIC is gated to `isOff || (m_isGen2 && Running)` (`ApplyStateGating`: `networkAddButton` + each card's `removeCheck`). Synthetic NIC hot-add/remove on a running Gen 2 VM is verified to work (add+remove succeeds, existing NIC untouched); the **Saved** state is excluded because Hyper-V silently rejects hardware adds there, and running **Gen 1** is excluded (legacy/synthetic NIC changes need the VM Off). Switch/MAC/VLAN edits on existing NICs stay **live** in every state.
    - **Advanced features (v14)** — MAC spoofing, DHCP guard, router guard, NIC teaming, and port mirroring all live on ONE more feature setting, `Msvm_EthernetSwitchPortSecuritySettingData` (bools `AllowMacSpoofing` / `EnableDhcpGuard` / `EnableRouterGuard` / `AllowTeaming`; `MonitorMode` UInt8 0=None/1=Destination/2=Source). Same Add/Modify-FeatureSettings layering on the allocation as the VLAN (`VMManager::SetNetworkAdapterAdvanced` writes the whole set at once; modify-if-present, else clone the `Definition\...\Default` template + AddFeatureSettings). A fresh NIC has **no** security setting until the first edit (so the per-poll read defaults all-off when absent). Live edits, no state gate. As with VLAN, `Get-VMNetworkAdapter`'s `PortMirroring`/etc. read-back lags a raw `ModifyFeatureSettings` by ~1s — raw WMI is authoritative.
    - **Bandwidth limits (v15)** are a *separate* feature setting, `Msvm_EthernetSwitchPortBandwidthSettingData` (`Limit`=max, `Reservation`=min, both UInt64 **bits/sec**; `VMManager::SetNetworkAdapterBandwidth`, same modify-or-add layering). UI is **Mbps**; stored bits/sec = Mbps × 1,000,000 (decimal millions — Hyper-V Manager's convention, verified the cmdlet round-trips it exactly). Caveat: an absolute `Reservation` (minimum) is only honored on a virtual switch in *absolute* minimum-bandwidth mode; a weight-mode switch rejects it (failed modify). `Limit` (max) always works. The dialog diffs at whole-Mbps granularity so a no-touch Save never rewrites a non-Mbps-aligned stored value.
    - **The "nothing changed → bail" guard in `VmSettingsDialog::OnPrimaryButtonClick` is a fifth edit site for ANY new editable field.** That early-`co_return` ANDs together every `p.*Changed` flag / `p.*.empty()` collection; if a new field isn't listed, a Save whose *only* change is that field short-circuits before the apply loops and silently no-ops (it appears to work only when combined with another change that makes the guard false). The NIC add/remove/VLAN fields hit exactly this on first build (caught by the user — a pure add/remove did nothing). **Adding an editable field to this dialog is FIVE coordinated edits: orig-snapshot in `LoadFromVm`, the control, the diff, the apply loop, AND this guard.** Sibling of gotcha #15.

## Memory / processor / NUMA

26. **`AutomaticShutdownAction` (stop action) is rejected while the VM is Running/Saved; `AutomaticStartupAction` (start action) is modifiable in any state.** Both live on the realised `Msvm_VirtualSystemSettingData` (start: 2=Nothing/3=StartIfRunning/4=Always; stop: 2=TurnOff/3=Save/4=ShutDown), written together by `VMManager::SetAutomaticActions` via `ModifySystemSettings`. But Hyper-V only lets the STOP action change when the VM is **Off** — change it while running and the *whole* combined modify silently no-ops (ret=4096 + clean job, applies nothing; the `Set-VM` cmdlet surfaces the same thing synchronously as `0x80041001` WBEM_E_FAILED). The disallowed stop change poisons the start change in the same call, so neither sticks — verified against live WMI (start-only `Set-VM` succeeds while Running; stop-only fails; both succeed Off). So `VmSettingsDialog::ApplyStateGating` gates ONLY the `autoStopCombo` to Off (`IsEnabled(isOff)`) and leaves `autoStartCombo` live in every state. Writing the stop property to its *unchanged* value while running is fine (it's only a *change* of the value that's rejected), which is why the combined setter is safe with the stop combo disabled — the diff keeps stop at its loaded value. Same silent-no-op family as gotchas #16/#7: a `Modify*Settings` that returns 4096 + a clean job but doesn't stick = Hyper-V silently rejected a property (wrong format, or a state gate). The start-delay (`AutomaticStartupActionDelay`) IS surfaced (v16) as a seconds field: it's a CIM datetime **interval** (`ddddddddHHMMSS.mmmmmm:000` — e.g. 90s = `00000000000130.000000:000`), written as that string via `WmiObject::Set(name, wstring)` (WMI accepts a string for a datetime property) and parsed back with the `Seconds<->CimInterval` helpers in `VMManager.cpp`. Like the start action, it's live in any state. (Sibling property `AutomaticSnapshotsEnabled` — "use automatic checkpoints", a plain bool on the VSSD — is surfaced in the Checkpoints section.)

31. **`Msvm_ProcessorSettingData.Reservation`/`Limit` are stored as percent × 1000 — the dialog must scale them, and the resource-control fields were never being loaded.** Hyper-V Manager's "Virtual machine reserve/limit (percentage)" shows `0–100`; the WMI stores **percent × 1000** (verified: WMI `Limit=100000` ↔ `Get-VMProcessor.Maximum=100`). The settings dialog now edits `0–100` and round-trips `÷1000` on load / `×1000` (`llround`) on save; `VMManager::ProcessorConfig.reservationPct`/`limitPct` stay **raw WMI** internally (so `SetProcessorConfig` writes WMI directly — don't "normalize" them there). HVM's derived **"Percent of total system resources"** = `perCpu% × vCPU / hostLogicalProcessors` (host LP via `GetActiveProcessorCount(ALL_PROCESSOR_GROUPS)`). **Separately:** until v19 the dialog *hardcoded* memory weight = 5000 and processor reserve/limit/weight = defaults in `LoadFromVm` — the boxes existed but never reflected the VM's real values, and the poll cache (`VirtualMachine`) doesn't carry them. Fixed with `VMManager::GetMemoryConfig`/`GetProcessorConfig` (fresh per-VM reads, like the security/boot-order live reads). **Lesson: a settings field whose value isn't in the poll cache needs an explicit fresh read in `LoadFromVm` — don't leave it defaulted, or it silently shows/writes the wrong value.** (`Msvm_MemorySettingData.TargetMemoryBuffer` is a plain percentage — default 20 — no scaling.) **NUMA (v20a):** max-per-node procs/nodes are `Msvm_ProcessorSettingData.MaxProcessorsPerNumaNode`/`MaxNumaNodesPerSocket` (uint64); **max memory per node is `Msvm_MemorySettingData.MaxMemoryBlocksPerNumaNode` where a "block" = 1 MB** (verified: host NUMA node `CurrentlyConsumableMemoryBlocks` ≈ host RAM in MB), so it's edited directly in MB. All Off-gated; `LimitProcessorFeatures` (bool) is the "Compatibility" checkbox. Gotcha-#26 corollary confirmed: writing an *unchanged* NUMA value while the VM is Running is accepted (`ret=0`), so it doesn't regress the live buffer/weight edits that share `SetMemoryConfig`.

## VM security (vTPM / encryption / shielding)

27. **vTPM / VM security: a valid key protector is a PREREQUISITE for changing ANY security setting, and `GetKeyProtector` returns a 4-byte placeholder (not empty) when none is set.** Per-VM security (`TpmEnabled`, `EncryptStateAndVmMigrationTraffic`) lives on `Msvm_SecuritySettingData`. All three knobs go through `Msvm_SecurityService` (a host singleton, NOT `Msvm_VirtualSystemManagementService`): `ModifySecuritySettings(<SSD CIM XML>)`, `SetKeyProtector(KeyProtector=uint8[], <SSD CIM XML>)`, `GetKeyProtector(<SSD CIM XML>) -> uint8[]`. **All three string params carry the `HyperVEmbeddedInstance=Msvm_SecuritySettingData` qualifier — pass `ssd.GetCimXml()`, NOT a `__PATH`** (checked the MOF qualifiers; getting this wrong is a silent-no-op trap). Key facts, each verified against live WMI:
    - **Finding the SSD**: it associates to the realised VSSD but **NOT via `Msvm_VirtualSystemSettingDataComponent`** (that's only resource settings — memory/processor/NIC/disk). Filter by ResultClass only: `vssd.GetAssociated(nullptr, L"Msvm_SecuritySettingData")` (== `Get-CimAssociatedInstance -ResultClassName`). `VMManager::FindSecuritySettingData`. Using the component assoc class returns nothing → "no SSD". The per-poll *read* instead batch-queries `Msvm_SecuritySettingData` directly and parses the VM GUID out of `InstanceID` (`Microsoft:<VMGUID>\<SUBGUID>`).
    - **Key-protector prerequisite**: Hyper-V refuses to change ANY security setting without a valid KP — the cmdlet error is literally *"the selected security settings of a virtual machine cannot be changed without a valid key protector configured."* This bites **state encryption too**, not just vTPM. Writing `EncryptStateAndVmMigrationTraffic=true` with no KP sets the config bit (raw SSD reads `True`) but it's NOT effective (`Get-VMSecurity` reads `False`) AND leaves the VM in a state that blocks further security changes. So `VMManager::EnsureKeyProtector` runs before the modify when *enabling* either feature.
    - **`GetKeyProtector` placeholder**: when no KP is set it returns a **4-byte blob `00 00 00 04`**, NOT an empty array (a real local KP is ~5183 bytes). An `existing.empty()` check sees the placeholder as "present", skips provisioning, and the enable then silently no-ops (ret=4096, clean job). Test `existing.size() >= 32`.
    - **Generating a local KP** lives in a SEPARATE namespace, `root\Microsoft\Windows\Hgs` (`VMManager::m_hgsScope`, lazily opened). `MSFT_HgsKeyProtector::NewByGuardians(Owner=<guardian>, AllowUntrustedRoot=true) -> cmdletOutput.RawData`. The owner is the host's `MSFT_HgsGuardian WHERE Name='UntrustedGuardian'`, auto-created via `MSFT_HgsGuardian::NewByGenerateCertificates(Name, GenerateCertificates=true)` when absent. Both are **static (class-level) methods** — invoke on the `GetClass(...)` object (its `__PATH` is the class path; `ExecMethod` accepts that). `Owner` is passed as an **embedded CIM instance** — `WmiObject::Set(name, WmiObject const&)` already does the `VT_UNKNOWN` dance, and `GetObject` reads `cmdletOutput` back; the only new primitives needed were `WmiObject::Get/SetUInt8Array` for the blob.
    - **State gate**: Off + Gen 2 only (`ApplyStateGating` gates the toggles; the nav item is hidden for Gen 1). After `SetKeyProtector` the SSD ref regenerates — re-fetch before the modify (same shape as gotchas #17/#23).
    - **Dialog reads security LIVE** (`VMManager::GetVmSecurity`) in `LoadFromVm`, NOT the 1 s poll cache. Scalar toggles read from the cache (secure boot, auto-actions) lag a Save by up to a poll cycle — reopening the tab right after saving showed stale values. Boot order / DVD / hard disks already read fresh in `LoadFromVm`; the security toggles now do too.

32. **VM shielding is a COMPOSITE write, and `ShieldingRequested` alone is a silent no-op.** `VMManager::SetVmShielded` writes `Msvm_SecuritySettingData.ShieldingRequested` via `Msvm_SecurityService::ModifySecuritySettings` (same path as `SetVmTpm`/`SetVmStateEncryption`, same `EnsureKeyProtector` prereq — gotcha #27). But setting **only** `ShieldingRequested=true` returns `ret=0` yet doesn't stick (`Get-VMSecurity.Shielded` stays False — the gotcha-#27 "config bit set but not effective" family). A shielded VM **requires** vTPM + encrypted state, so the enable path also sets `TpmEnabled=true` + `EncryptStateAndVmMigrationTraffic=true` in the same modify (verified by diffing the raw SSD before/after `Set-VMSecurityPolicy -Shielded $true`: the cmdlet flips `ShieldingRequested` AND `EncryptStateAndVmMigrationTraffic`). **Disable clears only `ShieldingRequested`** — Hyper-V leaves encryption on (the cmdlet does the same); the user turns encryption off separately. The dialog's `OnShieldingToggled` mirrors this in the UI (shielding-on forces the TPM + encryption toggles on and locks encryption on). Off + Gen 2 gated. **Verification caution:** `Get-VMSecurity` (cmdlet) **lags raw `ModifySecuritySettings` writes by >400 ms** — "didn't stick" reads were stale; our `VMManager::GetVmSecurity` uses a raw `Msvm_SecuritySettingData` query so it's fresh. When testing security mutations reversibly, capture+restore **all four** bits (`TpmEnabled`, `EncryptStateAndVmMigrationTraffic`, `ShieldingRequested`, `DataProtectionRequested`) and settle ≥2 s before trusting a cmdlet read. Full shielding needs HGS attestation; a local key protector is only a "soft" shield and may restrict host-console (VMConnect) access.

## Snapshots / checkpoints

34. **`ApplySnapshot` needs the VM Off/Saved (running → 32775); a snapshot's InstanceID is its OWN guid, so the parent VM guid can't be parsed from it.** Facts behind the snapshot apply/revert path, all verified reversibly on CACHY:
    - **State gate + save/resume:** `Msvm_VirtualSystemSnapshotService::ApplySnapshot` returns **32775 (invalid state)** on a **Running** VM, but works when **Off OR Saved** (both verified `ret=4096`, job state 7). `TakeSnapshot`/`DeleteSnapshot` work in any state (delete confirmed `ret=4096` on Running). So `VMManager::ApplySnapshot` applies directly when Off/Saved (no resume — leaves the VM as it found it, matching Hyper-V Manager); when **Running/Paused** it runs `SaveThenApplySnapshot` (detached MTA worker): **SAVE** (`RequestStateChange Offline=6`, wait `EnabledState==6` ≤120 s — saving RAM is slow), apply, then **START** (`Enabled=2`) to resume. A *failed* apply leaves the VM Saved, so the resume restores the **original** state (no data loss) — that's why we save rather than hard-off. The revert confirm just says "the current state will be lost" (no "turned off" text). Verified save→apply-while-Saved→start round-trips on CACHY.
    - **Snapshot InstanceID shape:** a snapshot VSSD's InstanceID is **`Microsoft:<SNAPSHOT-OWN-GUID>`** (a single guid), NOT `Microsoft:<VMGUID>\<SUBGUID>` like resource/security settings. So you **cannot** parse the parent VM guid out of a snapshot path — the first cut did (`SnapshotVmGuid`) and got the snapshot's own guid, so `MarkPendingStateChange` got a non-matching guid → no blink/banner for apply/delete. Fix: the **caller passes the VM guid** (`ApplySnapshot(vmGuid, path)` / `DeleteSnapshot(vmGuid, path, subtree)`); the info panel uses `m_flyoutVmGuid`, the context-menu revert already has it. (`ConfigurationID` on the snapshot VSSD *does* hold the VM guid but isn't WQL-filterable — `Get-CimInstance -Filter "ConfigurationID='…'"` returns nothing; filter by `InstanceID='Microsoft:<snapId>'` via the snapshot's `.Id` instead.)
    - **Rename:** a snapshot IS a `Msvm_VirtualSystemSettingData`, so `VMManager::RenameSnapshot` sets its `ElementName` + `ModifySystemSettings(snapVssd.GetCimXml())` — same shape as `RenameVM`, works in any state.
    - **Progress UX:** snapshot ops set `VirtualMachine::pendingJobLabel` ("Taking snapshot…" etc.) via `MarkPendingStateChange(guid, label)`; the dot pulses **blue** (vs green/amber for power ops) and the label is routed into `statusText` (when native is empty) so the home list / rail / flyout state line + the info-panel status all show it (upgrading to Hyper-V's native "Creating Checkpoint (35%)" when it appears). Labeled-op pending entries skip the poll's `moved`-clear (a revert's save moves state to Saved mid-op) — the watcher/worker is the authoritative clear. The watcher/worker calls **`KickPollAndWait` BEFORE clearing the status**, so the list is already fresh when the status disappears (otherwise the list lags a poll cycle behind). UI: the per-snapshot actions are a **right-click context menu** (Apply / Rename… / Delete / Delete subtree, job-gated on `Opening`); **Take** is a bottom-left button with the in-flight status inline to its right (no list shift). Rename input uses `hyprv::app::ui::ShowInputDialog` — note the ContentDialog `DefaultButton` doesn't fire Enter while a single-line TextBox is focused, so the input dialog hooks the TextBox `KeyDown` to accept on Enter.
    - **"Now" position marker:** `Msvm_MostCurrentSnapshotInBranch` links a VM (`Antecedent`) to the snapshot its live state currently descends from (`Dependent` — the "Now" parent). Verified it tracks the right node across linear / reverted-no-resnap / new-branch cases (whereas `Msvm_LastAppliedSnapshot` is only populated after a revert). The Dependent InstanceIDs are globally unique, so the read batches `SELECT * FROM Msvm_MostCurrentSnapshotInBranch` into a flat `unordered_set` and stamps `Snapshot::isCurrent` (no per-VM keying); the info-panel list renders a synthetic green "● Now" **child node** (depth+1, key `\x01now`, `IsHitTestVisible(false)`) under that snapshot — like Hyper-V Manager's tree, not a badge.

## COM (serial) ports

35. **Disconnecting a COM port must write `Connection=[""]` (a one-element empty string), NOT `[]` (an empty array) — the empty array is a silent no-op.** A virtual COM port is `Msvm_SerialPortSettingData` (ResourceType 21, ResourceSubType `Microsoft:Hyper-V:Serial Port`); every VM has exactly two (COM 1 / COM 2), they can't be added/removed. `Connection` is a **string array** holding the host named pipe (`Connection[0]`, e.g. `\\.\pipe\name`); the write is `ModifyResourceSettings` on the SASD (`VMManager::SetSerialPortConnection`, same shape as `SetDiskQos`/`SetDvdMedia`'s change path). **Connect** = `Connection=[pipePath]`. **Disconnect** is the trap: writing `Connection=[]` (an empty `SetStringArray`) returns `ret=4096` + a clean job but the value never changes — root-caused by diffing the serialized WMI DTD 2.0 XML against the cmdlet's: `<VALUE.ARRAY></VALUE.ARRAY>` (empty array) is silently ignored, but `<VALUE.ARRAY><VALUE></VALUE></VALUE.ARRAY>` (a single empty string) clears it (`ret=0`, and Hyper-V normalizes it back so a subsequent read returns `[]`). So `SetSerialPortConnection` always writes a **single-element** array — the pipe path, or `""` to disconnect. The silent-no-op family (CLAUDE.md #7/#16/#30). Verified reversibly on CACHY (Off) + ARCH (Running): the path write is **hot-settable** (no state gate), confirmed via raw `ModifyResourceSettings` with both formats.
    - **The host named pipe binds at VM power-on (cold start), not on the setting write.** Hyper-V's emulated UARTs "cannot be hot-added and aren't available for debugging unless ... configured with a pipe name" (MS docs). Setting/clearing the pipe on a running VM stores the config but the host pipe endpoint only (dis)appears on the next **power-cycle** (Turn off → Start). A *guest-OS reboot is NOT enough* — the VM worker process (which owns the pipe) stays alive across a soft reboot. Surfaced in the COM Ports dialog intro: "Changes take effect after the VM is turned off and started again."
    - **Generation 2 COM ports are debug-only.** Per MS docs, Gen 2 VMs do NOT present COM ports as PnP devices — they don't appear in the guest's Device Manager ("Ports (COM & LPT)") OR in Hyper-V Manager's VM settings; they exist purely for kernel/serial debugging. Gen 1 exposes them as normal `Communications Port (COMx)` devices. So "my COM port isn't in Device Manager" on a Gen 2 guest is **expected, not a bug**. Also: a COM port configured as the **kernel-debug port** (`bcdedit /dbgsettings serial debugport:N`) is hidden from Device Manager even on Gen 1 — Windows reserves it for the debugger (serial.sys won't claim it), so the *other* COM port is the only one that shows.
    - **Kernel-debug setup (Gen 2):** Secure Boot must be **off** (kernel debug is incompatible with it — flip it in the Security page), set the COM pipe while Off, **cold start**, then in the guest `bcdedit /debug on` + `bcdedit /dbgsettings serial debugport:N baudrate:115200` + reboot, and on the host (elevated) `windbg -k com:pipe,port=\\.\pipe\<name>,resets=0,reconnect`.

## Storage — physical disk (pass-through)

36. **Enumerating offline host physical disks for pass-through requires hyprv to run ELEVATED (full admin) — the Hyper-V Administrators group is NOT enough.** Hyper-V exposes a host physical disk as an `Msvm_DiskDrive` instance with a non-null `DriveNumber` *only when the disk is offline*; `VMManager::GetAvailablePhysicalDisks` queries those (each carries `devicePath` = the instance `__PATH`, `ElementName` for a label, `MaxMediaSize`). But **a non-elevated process — even one in the Hyper-V Administrators group that can do every other VM operation — gets back only the VM-attached synthetic drives** (empty `DriveNumber`); the offline host disk is invisible, so the picker is silently empty. Confirmed by the user: the identical offline disk is visible to an elevated query / in elevated hyprv and invisible to a non-elevated one. So the pass-through flyout is **elevation-aware** — when not elevated AND the list is empty it shows "Run hyprv as administrator to attach a physical disk." (`IsProcessElevated()` via `GetTokenInformation(TokenElevation)`), distinct from the genuine "No offline physical disks are available."
    - **Pass-through is a single-layer add** (unlike `AttachVhd`'s two layers): clone the default `Microsoft:Hyper-V:Physical Disk Drive` RT-17 template (a *dedicated* template, distinct from the VHD's "Synthetic Disk Drive"), set `Parent`=controller + `AddressOnParent`=slot + `HostResource`=[the host `Msvm_DiskDrive` `__PATH`], one `AddResourceSettings`. There is **no `Msvm_StorageAllocationSettingData` (VHD) layer** — that class is file-backed only. Verified reversibly: SASD count unchanged 1→1; `Set-VMHardDiskDrive -MinimumIOPS/-MaximumIOPS` ↔ raw `IOPSReservation`/`IOPSLimit` for the separate QoS feature (v22, normalized 8 KB IOPS, written verbatim, hot-settable).
    - **Detach reuses `DetachVhd` with an empty `vhdRef`** — its `removeOne` lambda no-ops on an empty ref, so it removes only the disk-drive RASD. `GetHardDisks` surfaces pass-through disks via a second loop (RT-17 RASDs with ResourceSubType "Physical Disk Drive", `isPassthrough=true`, `vhdRef` empty) since they don't appear in the VHD SASD query; the dialog omits the QoS row for them.
    - **The host disk must be offline + fixed.** Removable USB flash drives report `MediaType = Removable Media` and **can't be taken offline** (`Set-Disk -IsOffline $true` → "Removable media cannot be set to offline"), so they can't be passed through — only fixed disks (incl. USB external HDDs/SSDs that present as fixed). Verifying a *successful* attach reversibly needs an offline disk: mount a throwaway VHD (it presents as a fixed disk), `Set-Disk -IsOffline`, attach, inspect, detach, dismount.

## WinUI styling

37. **Stock-control chrome referenced via `{StaticResource}` in the control template CANNOT be compacted by an app-/page-level resource override.** A `{StaticResource}` is resolved exactly once, at template-parse time, against generic.xaml's own resources — so a local `<x:Double x:Key="ExpanderMinHeight">28</x:Double>` in a page/dialog ResourceDictionary is **silently ignored** (the template already baked in the 48). This bit the per-card "Settings" expanders (the dense NIC/disk cards): the default `Expander` header is 48 DIP, driven by `MinHeight="{StaticResource ExpanderMinHeight}"` on the header `ToggleButton`, with `Padding="{StaticResource ExpanderHeaderPadding}"` — both StaticResource. What actually works:
    - **Set `MinHeight` + `Padding` as LOCAL values on the Expander instance** (`exp.MinHeight(28)` etc.). A local value outranks the style setter (`<Setter Property="MinHeight" Value="{StaticResource ExpanderMinHeight}">`), and the header `ToggleButton` template-binds `MinHeight="{TemplateBinding MinHeight}"`, so the new value propagates through to the header.
    - **The chevron forces a floor that MinHeight alone can't beat:** `ExpandCollapseChevronBorder` is `Width/Height="{ThemeResource ExpanderChevronButtonSize}"` (default 32), so even at `MinHeight=28` the header stays ~32. But that one IS a `{ThemeResource}`, so a scoped `<x:Double x:Key="ExpanderChevronButtonSize">24</x:Double>` override works.
    - **General rule:** before trying to restyle a stock WinUI control via resource overrides, grep `generic.xaml` (`packages/Microsoft.WindowsAppSDK.WinUI.<ver>/lib/native/Microsoft.UI/Themes/generic.xaml`) for the key — `{StaticResource}` = override won't reach it (use a local value on the instance, or retemplate); `{ThemeResource}` = a scoped override works.

39. **A `ContentDialog` body taller than the default `ContentDialogMaxHeight` is CLIPPED, not scrolled.** The New VM dialog was built to the same footprint as the settings dialog (`Grid Width="1040" Height="620"`, `ContentDialogMaxWidth=1100`), but its single-column form scrolled-to-bottom cut off the last rows. Cause: the default `ContentDialogMaxHeight` is smaller than (body 620 + title + buttons + ContentDialog padding), so the dialog **compresses the content area below 620**; the fixed-height inner Grid then overflows the compressed area and its bottom is clipped, and the `ScrollViewer` inside can't scroll far enough to bring the last rows into view (they sit in the clipped region). Fix: override `ContentDialogMaxHeight` in the dialog's resources, exactly like `ContentDialogMaxWidth` — `<x:Double x:Key="ContentDialogMaxHeight">900</x:Double>` gives the 620 body + chrome room to render full-size, so the ScrollViewer constrains to its real height and scrolls all the way. ContentDialog still clamps to the window/XamlRoot on a short display, so the override is just a ceiling. (The settings dialog hasn't hit this because its two-pane sections are individually shorter than the compressed area.)

## VM creation (New VM wizard)

38. **A raw `Msvm_VirtualSystemManagementService::DefineSystem` VM ships BARE — no SCSI controller, no NIC, no DVD drive** — unlike the `New-VM` cmdlet, which provisions them. Verified reversibly (raw `DefineSystem` Gen 2 + Gen 1 → enumerate default RASDs → `Remove-VM`): a Gen 2 VM gets only keyboard/mouse/serial-controller + 2 COM ports + 1024 MB dynamic memory + 1 vCPU (**no `Microsoft:Hyper-V:Synthetic SCSI Controller`, no synthetic NIC, no DVD**); a Gen 1 VM gets its **two Emulated IDE Controllers** + a floppy controller (still no NIC / DVD). Consequences for `VMManager::CreateVM`:
    - **Gen 2 must `AddScsiController` BEFORE `AttachVhd`/`AddDvdDrive`** (those need a controller to land on); Gen 1 attaches straight to its IDE controllers.
    - `SystemSettings` for DefineSystem is a spawned `Msvm_VirtualSystemSettingData` — `m_scope->GetClass(L"Msvm_VirtualSystemSettingData")` → `SpawnInstance` → set `ElementName` + `VirtualSystemSubType` (`Microsoft:Hyper-V:SubType:1` Gen 1 / `:2` Gen 2) → `GetCimXml()`. Manual invoke (NOT the typed wrapper): `ResourceSettings`=empty `string[]` (memory/proc get defaults, then the verified `SetMemoryConfig`/`SetProcessorConfig` tune them), `ReferenceConfiguration` left NULL. The new VM's GUID comes from `out.GetString("ResultingSystem")` (a ref path) → `GetByPath().Name`, with a `Name="…"` substring-parse fallback.
    - Everything downstream reuses the **already-verified** Add\*/Set\* helpers (`SetMemoryConfig`, `SetProcessorConfig`, `AddScsiController`, `CreateAndAttachVhd`/`AttachVhd`, `AddNetworkAdapter`, `AddDvdDrive`+`SetDvdMedia`, `Get/SetBootOrder`), so CreateVM runs **on the UI/`m_scope` apartment** like the rest. Device steps are best-effort (a failure leaves a usable VM to finish in Settings, not an orphan).
    - **Custom VM location** ("store the virtual machine in a different location"): set `ConfigurationDataRoot` + `SnapshotDataRoot` + `SwapFileDataRoot` on the SystemSettings VSSD before DefineSystem. Verified: the VM config (`.vmcx`), checkpoints, and smart-paging file all root under that path and **Hyper-V auto-creates the directory**. The default is the host `Msvm_VirtualSystemManagementServiceSettingData.DefaultExternalDataRoot` (e.g. `V:\Hyper-V`); the default VHD dir is `DefaultVirtualHardDiskPath`.
    - **Install media boots first:** after `AddDvdDrive`+`SetDvdMedia(iso)`, `PromoteDvdToBootFront` reorders the boot order so the VM boots the installer (see gotcha #40). The DVD entry is found by device KIND, not by the cryptic description.

40. **Gen 2 boot entries are cryptic — correlate `Msvm_BootSourceSettingData` to its backing device for friendly labels AND to find the DVD by kind.** The realised VSSD's `BootSourceOrder` is a `string[]` of refs to `Msvm_BootSourceSettingData`, whose `BootSourceDescription` is the firmware-level name — **"EFI SCSI Device" / "EFI Network"**, NOT "DVD Drive". So `CreateVM`'s first DVD-promotion attempt (string-match `"dvd"`/`"cd"` against the description) **never matched** and the created VM didn't boot its install media. The correlation, verified read-only on a real VM:
    - A boot source's `InstanceID` is its **device RASD's `InstanceID` + `\B`** (e.g. boot source `…\<ctrlGuid>\0\1\D\B` ↔ disk-drive RASD `…\<ctrlGuid>\0\1\D`). Confirmed by the `Msvm_LogicalIdentity` association (`SameElement`=boot source, `SystemElement`=device RASD). Strip the trailing `\B` and look the device up in a map of the VM's RASD `InstanceID` → `ResourceType`.
    - `ResourceType` 17 = disk drive ("Hard Drive"), 16 = DVD drive; `BootSourceType` 2 = Network (no backing storage RASD). `GetBootOrder` tags each `BootEntry` with a `BootKind` (HardDrive/Dvd/Network/Other) + a friendly `description`, so `PromoteDvdToBootFront` finds the DVD by `kind == Dvd` (robust regardless of label wording) and the Firmware dialog shows "DVD Drive (install.iso)" / "Hard Drive (vm.vhdx)" / "Network Adapter".
    - To resolve the attached file for the label: the storage SASD's `Parent` value == the drive RASD's `__PATH` (BOTH full paths — `WmiObject::Path()` returns `__PATH`, which is the full `\\HOST\ns:Class.Key` form, and `Parent` is stored the same way), so a `drive __PATH → InstanceID` bridge + the SASD's `HostResource[0]` filename works. (Raw `InstanceID` keys use single backslashes; `__PATH`-embedded `InstanceID="…"` uses doubled backslashes — don't cross-match those; match `__PATH` to `__PATH` and `InstanceID` to `InstanceID`.)

## rdphost connection state machine

41. **Optimistic pre-connect on Start, and the keep-alive latch must NOT clear on `OnConnected`.** The console was coming up too late on a fresh VM's first boot — by the time the (cold) rdphost spawned after the poll noticed "Running", the firmware "Press any key to boot from CD" prompt had already timed out. Fix = pre-connect: clicking the placeholder Start button sets `m_pendingConnect` and spawns the rdphost immediately (before the poll reports Running), so mstscax attaches as the VM powers on (VMConnect-style) and catches the boot prompt. `UpdatePlaceholderAndClient` "wants a live client" when `vm.IsRunning() || m_pendingConnect`; a failed early attach (VM console not up yet) retries fast via `OnDisconnected`; the latch ages out after 25 s if a start never takes.
    - **The trap (root cause of the churn the user hit):** the optimistic connect can succeed BEFORE the poll's snapshot flips the VM to Running. If you clear `m_pendingConnect` in the `OnConnected` handler, the very next poll computes `wantClient = running(false) || pending(false) = false`, **tears the freshly-connected client down**, and then respawns a SECOND client once Running lands. Two mstscax attached to the same VM console → the new one kicks the old (`Disconnected disc=2`) → the console churns (spawn→connect→teardown→respawn→disc=2→reconnect…) and never stays up long enough to interact. The log signature was the tell: `spawning rdphost` (pid A, pending=1) → connected → `spawning rdphost` (pid B, running=1) → `disc=2` → auto-reconnect (pid C). **Fix: clear `m_pendingConnect` ONLY in `UpdatePlaceholderAndClient` once `vm.IsRunning()` (or on the timeout) — never on connect** — so the working connection persists continuously through the boot.
    - **Per-reboot recovery during install:** a Windows install reboots several times; each reboot drops the basic console session. Reconnect from a basic/console session is debounced **700 ms** (catches the post-reboot boot screen) vs **2 s** for enhanced (a too-quick enhanced reconnect thrashes an RDP negotiation that isn't ready; the 20 s enhanced cooldown — gotcha-area, see `m_enhancedCooldownUntil` — already routes a not-ready enhanced attempt to basic). `DoReconnect` proceeds when `running || m_pendingConnect`.

42. **Connect-error surfacing: classify on the child, gate on `wasConnected`, surface inline — never modal, never on every fatal drop.** Before this, `SetStatus` was log-only (the visible status line was removed when the project went pure-VM-display), so a failed connect was *invisible* — the pane either churned silently or went blank. The pipeline now:
    - **Child (`RdpHost::OnEvActDisconnected`)** classifies each mstscax disconnect: reason codes **0–3** (NoInfo / LocalNotError / RemoteByUser / ByServer) are benign; **`>3`** is `fatal` (socket / timeout / auth / cert / protocol). For fatal drops it calls `IMsRdpClient::GetErrorDescription(discReason, ext)` — the *same* localized text mstscax itself shows — and forwards it. This grew `Disconnected` from 8→16 bytes + a trailing UTF-8 string ⇒ **protocol bump to v2** (`kProtocolVersion`). Both EXEs ship together so the handshake always agrees; the change is wire-incompatible and must land atomically. Benign drops send `descByteLen = 0` to keep the common reboot/logoff frame small.
    - **Parent (`VmTabPage::OnDisconnected`)** does NOT surface every fatal drop — that would pop an error on every normal guest reboot. It captures `wasConnected = m_connected` *before* clearing the gate: an **established** session that drops (was Connected, any reason) is a benign reboot/logoff → reconnect quietly; only a connect **attempt** that **never reached `Connected`** and keeps failing `fatal` on a **Running** VM increments `m_connectFailures`, and only past `kMaxConnectFailures` (4) does it give up and surface. The optimistic pre-connect window (gotcha #41, VM still powering up) is *expected* failure and never counts. `m_hadConnectError` latches the error view so poll ticks + tab-switch-back keep it visible (instead of `UpdatePlaceholderAndClient` respawning a doomed client); it clears on a successful `OnConnected`, a user Start, a Retry, or the VM leaving a connectable state.
    - **Surface = the placeholder, inline, with a Retry button — not a `ContentDialog`.** A modal would spam during reconnect churn; the placeholder is exactly where the user looks when "the session isn't up". `RenderErrorPlaceholder` reuses the existing name/state/hint text blocks (state → "Connection failed" in `SystemFillColorCriticalBrush`, hint → the description) + a `placeholderRetry` button; the normal `showPlaceholder` lambda resets that chrome (hide Retry, state back to `TextFillColorSecondaryBrush`) so the two presentations don't bleed.
    - **`Error` codes** (HostStartupFailed / ProtocolError / BasicSessionWithShieldedVm — only HostStartupFailed is currently emitted, on a failed `Connect()` HRESULT) are terminal; the parent maps `RdpErrorCode` → a friendly string and rides the same Retry path.
    - **Built for reuse:** the classification + description + inline-surface pipeline is exactly what the Tier-2 **Remote Hosts** feature needs (generic RDP, where bad-creds / unreachable / cert errors are real and frequent), so that work just consumes `DisconnectedInfo.{fatal,description}` rather than reinventing it.

55. **Enhanced session must CONNECT at the full Border size — do NOT rely on a post-login `UpdateSessionDisplaySettings` to fit-to-window, because mstscax rejects that resize with `E_UNEXPECTED` (0x8000FFFF) for SECONDS after `OnLoginComplete` on a reconnect.** Symptom (user-reported, reproduced): the FIRST login to an enhanced VM fit the window fine, but after closing the tab and reopening + logging in again, the session stayed at the small ~1024×768 connect size and only expanded after the user manually wiggled the window a few times. Root-caused with per-call HRESULT logging + millisecond timestamps in the log (both added for this — `RdpHost::OnUpdateSessionDisplaySettings` now logs every call's `hr` via the IPC-forwarded `HyprvLog`, and `HyprvAppLog` prefixes every line with `[HH:MM:SS.mmm]`):
    - mstscax returns **`E_UNEXPECTED` from `UpdateSessionDisplaySettings`** until the guest's dynamic-display virtual channel is up. On a **fresh first connect** that channel is ready ~0.5s after `OnLoginComplete` (the first retry lands). On a **reconnect** (close-tab → reopen → relogin) the guest is re-establishing the channel and it took **~6.7s** — during which EVERY call fails identically **regardless of the requested size** (the manual window-drag resizes failed too; it only "worked" because the user happened to still be dragging when the channel finally came up). So the failure is purely **time-gated guest-channel readiness**, NOT a size/dedup issue — host-side can't speed up the guest.
    - **The connect-time `put_DesktopWidth/Height` (initial RDP negotiation), by contrast, is ALWAYS honored immediately** — both connects came up at exactly their requested connect size with no delay and an instant `OnRemoteDesktopSizeChange`. So the fix is: in `VmTabPage::StartConnection`, when the Border is already measured (the common reopen case — logs show `border=OK`), set `opts.desktopWidth/Height = bw/bh` (the full Border) so the enhanced session is full-size from the first frame. Confirmed by the user: instant fit on relogin, no resize, no letterbox (for ENHANCED, framebuffer = popup = Border, so a full-size framebuffer can't letterbox — the letterbox risk in gotcha #1 is a *basic*/SmartSizing concern).
    - **The cold-start fallback (Border not yet measured — gotcha #14 race) still uses the scaled 1024×768 placeholder** so the guest's logon UI centers in a sane logical desktop (gotcha #49 — that tuning only governs the *not-measured* path now; at full Border size the logical desktop is larger, the opposite of #49's cramped-682×512 problem, so logon centers fine — re-verify at >100% DPI if ever in doubt).
    - **`VmTabPage::StartEnhancedFit` (the repeating post-login retry) stays as a SAFETY NET, not the primary mechanism.** It re-pushes `UpdateSessionDisplaySettings(bw, bh±1px nudge)` on a 200ms timer for ~12s, stopping when `OnDesktopResized` confirms the session reached the Border. It now only matters for (a) the cold-start fallback path and (b) the rare window-resized-during-login case. The 1px nudge is because once mstscax IS ready it acts on a size DELTA, and clearing the `RdpHostClient` short-circuit cache (`InvalidateSessionDisplayCache`) alone isn't enough — but the nudge/retry is moot for the common path now that connect lands full-size. Tightening the retry interval (500→200ms) did NOT measurably help the reconnect case (the wall is `E_UNEXPECTED`, there's nothing to catch sooner) — connecting at full size is what fixed it.

57. **Kernel-debugger workflow: disable mstscax's built-in auto-reconnect, and don't let an established/enhanced session's transient drop downgrade it.** A user who breaks into a KERNEL DEBUGGER freezes the guest CPU — the VM stays **Running** in Hyper-V terms, but the guest-side RDP stack stops, so frames stop and the transport eventually drops. Three separate things conspired to make this a bad experience; all three are now fixed in `RdpHost::OnConnectLocalVm` / `VmTabPage::OnDisconnected`:
    - **mstscax's built-in auto-reconnect was ON by default** (never set), so a stall showed the Microsoft *"The connection has been lost. Attempting to reconnect your session…"* overlay and ran mstscax's OWN internal retry loop WITHOUT firing `OnDisconnected` — so hyprv never learned the session stalled (couldn't show its own placeholder) AND mstscax's internal reconnect state competed with / slowed hyprv's reconnect on debugger-resume. Fix: `adv6->put_EnableAutoReconnect(VARIANT_FALSE)` in BOTH `OnConnectLocalVm` (VM console) and `OnConnect` (Remote Hosts). Lives on `IMsRdpClientAdvancedSettings2` (inherited by the `adv6` we already hold). Now a stall surfaces promptly as `OnDisconnected` → hyprv hides the dead surface, shows its placeholder, and drives its own debounced reconnect on a fresh control.
    - **The connect-error escalation (gotcha #42's `kMaxConnectFailures`) would latch the "Connection failed / Retry" view** after 4 fatal connect failures — but during a long freeze the reconnect attempts fail repeatedly against the frozen-but-Running guest, so it gave up and stopped auto-recovering. Fix: a new `m_everConnected` flag (set on first `OnConnected`, never reset) — once a tab has connected at least once, a later run of fatal failures on a still-Running VM is treated as a transient (resets the counter, keeps retrying) instead of escalating. A never-connected tab still escalates (genuinely bad/unsupported console).
    - **The enhanced→basic cooldown (`m_enhancedCooldownUntil`) would downgrade to a basic session** for 20s after an enhanced drop — wrong for a debug break, where you want to come straight back to enhanced. Fix: a new `m_everEnhanced` flag — set when an enhanced session reaches **Connected** (NOT just `OnEnhancedReady`/login-complete, so breaking AT the enhanced login screen still counts), never reset. The cooldown is skipped entirely once `m_everEnhanced` holds. The cooldown still applies to a never-enhanced tab (OS install / first boot), where basic is the right fallback to catch the boot screen.
    - **Background-resume repaint was attempted and BACKED OUT.** When the parent reconnects while hyprv is NOT foreground (user resumed the debugger while tabbed away), the reconnect completes and `ShowNow` runs (`SW_SHOWNOACTIVATE`, confirmed via log: `ownerFg=0 ownerMin=0`), but mstscax's DirectX-composed surface doesn't re-present until the owner window is activated. Multiple nudge attempts were tried and reverted: parent-side `RedrawWindow` (cross-process, no effect on the child's DX surface); parent-driven 1px `WM_SIZE` jiggle (child received real `WM_SIZE` events — logged — but still no present); a child-side `RefreshSurface` IPC + in-process invalidate/size-nudge (surfaced the LIVE desktop but NOT the static pre-login credential framebuffer); and synthetic in-process activation (`WM_NCACTIVATE`/`WM_ACTIVATE`/`WM_SETFOCUS` — REGRESSED the working post-login case). All removed [user]: not worth it — once the user continues in the debugger they click/tab back to hyprv within moments, which repaints it anyway. The surface is genuinely gated on owner-window activation and can't be forced cleanly from outside without risking focus-steal / z-order surfacing over other apps. **If revisited, the `ShowNow` diagnostics (`owner=/ownerFg=/ownerMin=`) and a millisecond-timestamped log are the tools that proved the reconnect-completes-but-doesn't-paint behavior.**

58. **The VM tab's name + status is ONE always-present centered surface (`infoRoot`), not a name watermark + a separate placeholder.** A first cut had a dim always-on `backgroundVmName` watermark (for the case the popup is hidden + to feed the DWM taskbar thumbnail, which captures THIS XAML window, not the separate cross-process rdphost popup) PLUS a `placeholderRoot` that drew its own brighter name — so any non-connected state drew the VM name TWICE, overlaid, with different font/colour/position (the user caught it). A second cut added a separate cold-start `loadingOverlay` spinner that drew "Loading…" ON TOP of the watermark's "Loading…" — doubled again. **Settled design: a single `infoRoot` Grid (two equal rows split at vertical centre) that is NEVER collapsed.** Row 0 bottom-anchors `placeholderVmName` (so the name sits just above centre and never moves whether or not a status line is present); row 1 top-anchors a `placeholderStatusGroup` (spinner + state line + hint + Start/Retry buttons), each child toggled per state. `SetPlaceholderVisible(bool)` toggles only the status group + `infoRoot.IsHitTestVisible` (so the transparent surface can't eat clicks in the popup's letterbox margins during a live session) — it does NOT collapse the name. The name is always drawn exactly once, same appearance in every state, and still lands in the taskbar thumbnail when the popup covers it on-screen. `UpdateVmTabHeader` keeps `placeholderVmName` in sync with the live name (and the TabViewItem header). There is no separate watermark or loading-overlay element anymore.

## Remote Hosts (generic RDP)

43. **Generic RDP (`RdpHost::OnConnect`) is a different beast from the VM console (`OnConnectLocalVm`) — and `PromptForCredsOnClient` is on `IMsRdpClientNonScriptable4`, not 3.** A Remote Host is a real RDP server on `:3389`; the Hyper-V console is the VMBus endpoint on `:2179`. `OnConnect` was a stub until this feature. The setup splits cleanly:
    - **Reuse from the VM path:** ColorDepth, Desktop W·H, `SmartSizing=FALSE`, `KeyboardHookMode=1` (Win-key passthrough — gotcha #24), audio + redirection flags, DPI scale (`DesktopScaleFactor` / `DeviceScaleFactor`).
    - **Drop (VMBus-console only):** `put_PCB`, `put_AuthenticationServiceClass("Microsoft Virtual Console Service")`, RDPPort 2179, `put_NegotiateSecurityLayer(FALSE)`, `EnableFrameBufferRedirection`, `EnhancedMode`. Setting any of these against a real RDP server is wrong.
    - **Add:** `put_Server(host)`, RDPPort 3389.
    - **Credential model = "prompt every time" [user choice].** NO password is stored or sent on the wire. Set `put_EnableCredSspSupport(TRUE)` (on `IMsRdpClientNonScriptable3`) + `put_PromptForCredsOnClient(TRUE)` (**on `IMsRdpClientNonScriptable4` — a build error on NonScriptable3 sent me to grep the generated `src/obj/.../mstscax.tlh`; the declaring interface is the `struct __declspec(uuid(...))` immediately above the method**). mstscax then shows its own client-side NLA credential prompt. The scriptable interface has no `put_Password`; the password would otherwise live on the non-scriptable `IMsRdpClientNonScriptable::put_ClearTextPassword` — deliberately unused.
    - **Do NOT pre-set `put_UserName` / `put_Domain` [user-reported].** With NLA + `PromptForCredsOnClient`, supplying a username but no password makes the control attempt an authentication pass with incomplete creds (or the logged-in user's SSO), the server rejects it, and the credential dialog then appears carrying **"The logon attempt failed"** before the user has typed anything. Supplying NO credentials lets the control show a CLEAN prompt first. Cost: the saved username doesn't pre-fill the *first* prompt; Windows remembers it via its own `TERMSRV/<host>` store for subsequent connects. (The username still rides the v3 wire field + is logged for diagnostics — just not applied to the control.)
    - **Wire:** the username rides a **v3 field** — `RdpOptions.userByteLen` + a trailing UTF-8 username after the existing server/domain bytes; `RdpHostClient::Connect` gained a `username` param.
    - **`RemoteHostTabPage`** is a leaner clone of VmTabPage's connection half (no VM state / enhanced negotiation / WMI poll / optimistic pre-connect): connects on load, initial desktop = the window size, single Connect/Reconnect/Retry action on the placeholder. Adding the tab type means a branch in **all 7 MainWindow discrimination sites** (`OnTabSelectionChanged`, `CloseTabItem`, `PersistOpenTabs` → `type="rdp"`, `RestoreOpenTabs` → only if the host is still saved, `Push/PopPopupSuppression`) PLUS a `WindowSubclassProc` popup-bounds refresh (because `ActiveTab()` resolves only `VmTabPage`, so a remote tab's popup wouldn't follow window moves otherwise).
    - **Settings:** a `remoteHosts` JSON array of `RemoteHost { name, address, username, domain, port, rdp }` (nested `rdp` object — mirror of `recents` + `rdpDefaults`). Address is the case-insensitive key. No password persisted.
    - **The one live-only unknown:** whether mstscax's NLA credential prompt renders correctly inside the embedded out-of-process popup. Code builds + launches; the prompt UX needs a real RDP target to confirm.
    - **Build note:** the parallel PCH build OOM'd ("Failed to create virtual memory for PCH" / "internal heap limit reached" / "paging file too small") when many `cl.exe` each loaded the huge WinRT PCH. Recover with a serialized build: `-m:1 -p:CL_MPCount=1`.

## Tab tear-away / multi-window

44. **Tear-away uses the LEGACY drag-drop model (decide-on-release), NOT native `CanTearOutTabs`.** The two are mutually exclusive. `CanTearOutTabs` (WinAppSDK 1.6+) **pre-creates and positions the torn window under the cursor mid-drag** — a visible flash, with placement committed *during* the drag — which the user explicitly rejected; it also misbehaved here (the tab failed to move, left a blank window). The legacy model gives the wanted UX: **no window until the mouse releases, placement decided on release.** Markup: `CanDragTabs=True CanReorderTabs=True AllowDrop=True` on the TabView (NOT `AllowDropTabs` — it claims the strip+footer but only raises drop events over the actual tabs, leaving the empty title-bar a dead zone) + `TabDragStarting` / `DragOver` / `Drop` / `TabDragCompleted`. `rootGrid` and the title-bar footer (`titleBarTrailing`) are their own `AllowDrop` targets with `Background="Transparent"` — a null / `ClearValue` background is NOT hit-testable in empty areas; Transparent is, and still shows the backdrop through.
    - **Identify the grabbed tab by HIT-TESTING the cursor, not `args.Tab()`.** Pages live in `TabViewItem.Tag()` (Content empty, mounted into `tabContentHost` on selection); this page-in-Tag model breaks the framework's drag identification — `args.Tab()` reports the first tab. `TabUnderCursor()` transforms each tab's bounds into the window and tests the cursor (screen → client → DIP via `GetDpiForWindow`); the result is stashed in a same-process static `g_dragItem`. (Custom `DataPackageView.Properties` keys are NOT reliable same-process — don't gate on `HasKey`; use the static.)

45. **NEVER restructure the tabs inside a drag event — defer to the next dispatcher turn, or you WEDGE the TabView (a hang requiring a kill).** Removing the dragged `TabViewItem` from `TabItems()`, or spawning a whole new `MainWindow`, *synchronously* inside `Drop` / `TabDragCompleted` mutates the collection while the TabView's drag state machine is still unwinding on the stack. The framework's post-drag cleanup then finds the item gone, leaves its drag adorner painted on-screen (a phantom tab floating on the desktop), and never resets the "drag in progress" flag — so no further drag can start. A full-thread dump of the "hang" showed **no deadlock**: the UI thread was in the normal message pump and every worker was in its normal wait — the symptom was purely the wedged control. Fix: each handler computes its decision synchronously (read positions off `e` while it's valid) but posts the actual `MoveTabToThisWindow` / `SpawnWindowForTab` via `m_uiQueue.TryEnqueue([...]{ ... })`. The dragged item is captured strong so it survives the one-turn gap; the drag fully tears down (adorner destroyed, state reset) before the reparent runs.

46. **The custom title bar is a Win32 caption (non-client) — OLE drag-drop canNOT drop onto it. Route caption / desktop releases via `DropResult == None`; do NOT try to make the caption droppable mid-drag.** `ExtendIntoTitleBar` does `SetTitleBar(dragRegion)`, which registers that wide title-bar area as the OS caption. OLE drop targets are client-area only, so over the caption the OS draws a no-drop cursor and delivers no drop (over the actual tabs it works — interactive children are auto-excluded from the caption).
    - **A release over a caption / the bare desktop produces `DropResult == None`** (no drop target accepted it). `OnTabDragCompleted` routes None by cursor hit-test (`WindowUnderPoint`, gotcha #47): over another window's title bar → move into it; over the desktop / a foreign window → tear out. A `Move` result means an OLE drop (over tabs / body) or a same-window reorder already handled it — **return early** (this is what stops a just-reordered tab from being re-torn).
    - **Do NOT dynamically clear the caption during the drag to make it droppable.** Toggling `SetTitleBar(null)` + `InputNonClientPointerSource.ClearRegionRects(Caption)` in `TabDragStarting` (restore in `TabDragCompleted`) was tried and REGRESSED: re-registering the window's input regions *while the first drag's hit-testing was already running* broke drops AND reordering on that first drag (the second worked because the state had settled). Reverted. The no-drop cursor briefly shown over the title bar during a drag is a **cosmetic OS limitation** — the drop still works on release via the None path.

47. **`WindowUnderPoint` = topmost window (`WindowFromPoint` → `GA_ROOT`, NO `GW_OWNER`) + a title-bar BAND check — only the chrome is a move-in target, the body is not.** The rdphost surface is a **separate cross-process window covering the body**, so a release over the RDP content produces `DropResult == None` and lands in `WindowUnderPoint`. Resolving the popup's owner (`GW_OWNER`) back to the main window wrongly made the RDP content count as "over that window" — snapping a tab in over another window's content, and refusing to break a tab away over its own. Fix: take the top-level window directly under the cursor (no owner walk) AND require the cursor Y to be within the title-bar / tab-strip **band** (row 0 = the TabView's `ActualHeight`, in screen coords via `ClientToScreen`). Body releases (XAML content OR the rdphost surface) return null → tear out / break away.
    - **Lone-tab rule:** a window's ONLY tab never tears out into a NEW window — `SpawnWindowForTab` bails (it would just recreate the same window) — but moving a lone tab INTO another window (title bar or tab strip) IS honored (the source then empties → a secondary closes, the primary shows a welcome tab). A loose lone-tab release (desktop / foreign / its own window) is a no-op.
    - **Focus:** a torn-out window must reassert `SetForegroundWindow` on a **Low-priority dispatcher turn** — the source re-asserts foreground after a synchronous attempt (removing the tab re-selects / focuses the source), so last-writer-wins needs the deferred call. Symmetrically, a no-op lone-tab release reasserts the SOURCE window's foreground (dragging over another window had activated it).

48. **Multi-window plumbing: a strong-ref `WindowManager` registry, an `m_isPrimary` persistence gate, multicast `VMManager` callbacks, `AdoptMovedTab` re-wiring, and explicit rdphost teardown on a secondary's Close.**
    - **`ui/WindowManager.{h,cpp}`** — a function-local-static `vector<Window>`; `Track` pushes + wires `w.Closed` to `erase_if`; `Find(WindowId)` / `All()` / `Count()`. The primary is tracked in `App::OnLaunched`, each torn window in `SpawnWindowForTab`. Without the strong ref a torn window is collected.
    - **`m_isPrimary` (default true) / `MarkSecondary()`** — geometry + `openTabs` are a SINGLE global `Settings` blob, so a secondary must NOT persist (it would corrupt the primary's restore). A secondary skips `ApplyPersistedGeometry` + `RestoreOpenTabs` on activate and early-returns from the persist paths. **Accepted v1 limitation: torn windows are not session-persisted across launches** — only the primary restores its tabs.
    - **`VMManager` callbacks are MULTICAST** (`AddOnChanged` / `RemoveOnChanged` + `AddOnError` / `RemoveOnError`, token + `vector<pair>` fan-out). The old single-sink `SetOnChanged` (replace, not add) starved every window but the last-activated once a 2nd window opened → stale rails / flyouts / tab-headers. Each `MainWindow` subscribes on activate, unsubscribes on `Closed`.
    - **`AdoptMovedTab`** re-wires a moved item to its new window: VM/Remote → `SetWindowHwnd` (re-owns the popup, below) + `SetTabItem` + rebuild `ContextFlyout` with the new `get_weak()`; Welcome/Settings → `SetMainWindow(get_weak())`; AppSettings cross-window dedup (close the older). It resolves its own HWND first (the move can precede the new window's `OnActivated`) and `UnmountFromCurrentHost` detaches the page from the source `tabContentHost` before re-mount (a XAML element has one parent). `HandleSourceAfterDetach`: an emptied secondary closes, an emptied primary opens a welcome tab.
    - **`ShutdownAllTabClients()` on the window `Closed` handler** — closing a SECONDARY window doesn't exit the process, so the kill-on-job-close job that reaps rdphost on app-exit won't fire; without an explicit teardown a torn-off window's `hyprv-rdphost.exe` orphans (the `VmTabPage` dtor is only a best-effort net).
    - **Popup re-own = a parent-side Win32 call, NOT IPC.** `RdpHostClient::Reown(HWND newOwner)` = `SetWindowLongPtrW(childHwnd, GWLP_HWNDPARENT, newOwner)` + invalidate the reposition cache (`lastSx = INT_MIN` …) so the next bounds update actually moves the popup. `VmTabPage` / `RemoteHostTabPage::SetWindowHwnd` call it when the HWND changes and a client is live. No protocol bump, no rdphost change.
    - **`get_self` gotcha:** `MainWindow::get_weak().get()` yields the **impl** type directly (its impl methods aren't in the IDL — only `MyProperty` is), so call impl methods straight off it (like `self->OnVmManagerChanged()`). `winrt::get_self<MainWindow>(x)` is for **projected** objects only (from `make<>` / `try_as<hyprv_app::MainWindow>`) and mis-casts an impl → C2440 producer-conversion.

## MSIX / release / packaging / robustness

50. **Ship FRAMEWORK-DEPENDENT MSIX, not self-contained — self-contained is broken for this WinUI stack.** A hand-packed self-contained MSIX (and the single-project `WindowsAppSDKSelfContained=true` path) fail-fast at WinUI startup: the tooling doesn't merge the framework's resources into the package, so the first XAML load can't locate `ms-appx:///Microsoft.UI.Xaml/Themes/themeresources.xaml` → `combase` `0x802b000a` / `CLASS_E_CLASSNOTAVAILABLE` (windbg `!analyze` on a user dump confirmed the missing-resource fail-fast). Fix: framework-dependent. `src/package/Package.appxmanifest` declares `<PackageDependency Name="Microsoft.WindowsAppRuntime.2" MinVersion="2.1.3.0" Publisher="CN=Microsoft Corporation, …" />`; the target must have that runtime (the `.appinstaller` auto-installs it — #51). Packaging is a `.wapproj` (`src/package/hyprv-package.wapproj`, `EntryPointProjectUniqueName=..\app\hyprv.vcxproj`); rdphost is included as `<Content>` from `bin\$(Platform)\` (NOT a ProjectReference — that drops a duplicate in a `hyprv-rdphost/` subfolder), so `make-msix.ps1` builds rdphost first. Debug stays unpackaged (`WindowsPackageType=None`).
    - **Sign the BUNDLE once via Azure Trusted Signing.** `signtool sign /v /fd SHA256 /tr http://timestamp.acs.microsoft.com /td SHA256 /dlib <Azure.CodeSigning.Dlib.dll> /dmdf <metadata.json> <bundle>`. The dlib comes from the `Microsoft.Trusted.Signing.Client` NuGet (auto-fetched to `dist/.tools`); the metadata JSON is `{Endpoint, CodeSigningAccountName, CertificateProfileName}`. `DefaultAzureCredential` uses the signer's `az login` session; the account needs the **"Trusted Signing Certificate Profile Signer"** RBAC role. The bundle signature covers every contained `.msix` (no per-package signing). The signtool/dlib prints several "Signing completed" lines for one bundle — that's the dlib's multi-digest, not redundant signing. **Never handle the maintainer's Azure credentials — they `az login`; the build runs signtool against that session.** All of this is in `tools/make-msix.ps1`; never hand-pack.

51. **`.appinstaller` is a per-release VERSIONED manifest, NOT a static "install latest" pointer — and its `<Dependencies>` is what auto-installs the runtime.** App Installer's update check re-fetches the `.appinstaller` from the **root `Uri`** it was installed from and compares THAT file's **root `Version`** to the installed one; it never inspects the `.msix` version itself. So:
    - The root `Uri` is the STABLE `https://github.com/jxy-s/hyprv/releases/latest/download/hyprv.appinstaller` (the installed app re-polls it forever; `latest/download` always resolves to the newest release's asset). `<MainBundle>` / `<Dependencies>` `Uri`s are IMMUTABLE per-tag (`releases/download/v<ver>/…`).
    - All three versions bump together every release: manifest `<Identity Version>` = `.appinstaller` root `Version` = `<MainBundle Version>`. `tools/set-version.ps1 X.Y.Z.W` stamps the manifest Identity + both `.rc` FILEVERSION/PRODUCTVERSION; `make-msix.ps1` reads the manifest version into the `.appinstaller` (root + MainBundle) + the release tag.
    - **`<Dependencies>` auto-installs the WinApp runtime** (only if a satisfying version isn't already present) → this is what removes the manual `WindowsAppRuntimeInstall.exe` step and the `0xc000027b` first-launch crash on clean machines. You **host the framework `.msix` yourself** — Microsoft serves only the installer `.exe` + a redist `.zip`, never a bare `.msix` at a stable URL. `make-msix.ps1` stages `Microsoft.WindowsAppRuntime.2.msix` (41 MB) from the restored NuGet (`packages\Microsoft.WindowsAppSDK.Runtime.2.1.3\tools\MSIX\win10-<arch>\`).
    - Use the **2021 schema** (`xmlns=…/appinstaller/2021`); VS's default 2017/2 silently ignores `ShowPrompt`/`UpdateBlocksActivation`. `UpdateSettings`: `<OnLaunch HoursBetweenUpdateChecks="0"/>` + `<AutomaticBackgroundTask/>` (forward-only, silent for packaged desktop apps).
    - **The `ms-appinstaller:` web-install protocol is DISABLED by default since Dec 2023** (MSRC, after threat-actor abuse) and needs an enterprise Group Policy to re-enable — so DON'T build a one-click web button. Distribution = **download the `.appinstaller` and double-click**. GitHub Releases serves assets as `application/octet-stream` over a 302 to a CDN; that's fine for double-click install AND for the auto-update HTTP fetch (byte-range + Content-Length present; App Installer follows the redirect). Generated from `src/package/hyprv.appinstaller.template` (tokens `{VERSION}`/`{TAG}`/`{PUBLISHER}`; `make-msix.ps1` substitutes + fails the build if any token survives) → `dist/hyprv.appinstaller`, written UTF-8 **no-BOM, ASCII only** (App Installer rejects a BOM / non-ASCII).

52. **Multi-arch (x64 + ARM64) = ONE `.msixbundle` via `<MainBundle>`.** A `.appinstaller` allows only ONE `<MainPackage>`/`<MainBundle>` (the `<Dependencies>` list can hold many, but the *app* slot is singular), so two loose per-arch `.msix` can't share a descriptor — they must be bundled. `make-msix.ps1` builds each arch's `.msix`, stages them in a temp dir, `makeappx.exe bundle /d <dir> /p hyprv.msixbundle /bv <ver> /o`, then signs the bundle; the `.appinstaller` references it via `<MainBundle>` (no `ProcessorArchitecture` — App Installer auto-selects the device's arch from the bundle). Required project changes:
    - **rdphost** needed `Debug|ARM64` + `Release|ARM64` ProjectConfigurations added (it was x64-only). It's otherwise platform-agnostic (settings keyed on `$(Configuration)`, `OutDir` uses `$(Platform)`), so that was the only edit.
    - **The app `.vcxproj` `OutDir`/`IntDir` were conditioned on `Debug|x64`+`Release|x64` only** → ARM64 fell to the default and landed in a stray `<repo>\ARM64\Release\hyprv\` instead of `bin\ARM64\Release\`. Made them an unconditional `<PropertyGroup>` (`$(SolutionDir)bin\$(Platform)\$(Configuration)\`) so every arch lands consistently.
    - **The `.wapproj` rdphost `<Content>`** pulls from `bin\$(Platform)\$(Configuration)\` (was hardcoded `bin\x64\`), so each arch package carries its own-arch child.
    - **Both arches' runtime framework `.msix`** are declared in `<Dependencies>` (`ProcessorArchitecture="x64"` / `"arm64"`); App Installer downloads only the matching ~41 MB one. Hosted as `Microsoft.WindowsAppRuntime.2-{x64,arm64}.msix` release assets. (Download waste for the user is ~1.4 MB — the bundle carries both *app* arches but only the matching one installs; the big runtime is per-arch.)
    - Dropped the unused `Microsoft.WindowsAppSDK.AI` NuGet (hyprv uses no AI APIs). It's a transitive dep of the `Microsoft.WindowsAppSDK` umbrella, so removing it also needs `<WindowsAppSDKVerifyTransitiveDependencies>false</…>` in the app vcxproj (the umbrella's build verifier errors otherwise — Microsoft's own documented escape hatch). `.ML` / `Microsoft.Windows.AI.MachineLearning` are still present.

53. **Real `%LOCALAPPDATA%\hyprv` under MSIX needs BOTH a path fix AND a write-virtualization opt-out — either alone silently lands the file in the package LocalCache.** MSIX applies TWO independent redirections to AppData for a packaged process:
    - **Path:** `SHGetKnownFolderPath(FOLDERID_LocalAppData)` returns the package-redirected LocalCache path. Pass **`KF_FLAG_NO_PACKAGE_REDIRECTION`** (`| KF_FLAG_CREATE`) to get the un-redirected real path.
    - **Write:** even given the real path, AppData *writes* are virtualized into `…\Packages\<pfn>\LocalCache\Local\…`. Disable via the **`unvirtualizedResources`** restricted capability + a `FileSystemWriteVirtualization` exclusion in `Package.appxmanifest`:
      ```xml
      <!-- namespaces: xmlns:desktop6=".../desktop/windows10/6"  xmlns:virtualization=".../virtualization/windows10" -->
      <Properties>
        <desktop6:FileSystemWriteVirtualization>disabled</desktop6:FileSystemWriteVirtualization>   <!-- Win10 1903+ (coarse) -->
        <virtualization:FileSystemWriteVirtualization>                                               <!-- Win11/20348+ (fine) -->
          <virtualization:ExcludedDirectories>
            <virtualization:ExcludedDirectory>$(KnownFolder:LocalAppData)\hyprv</virtualization:ExcludedDirectory>
          </virtualization:ExcludedDirectories>
        </virtualization:FileSystemWriteVirtualization>
      </Properties>
      <Capabilities> … <rescap:Capability Name="unvirtualizedResources" /> </Capabilities>
      ```
    - **The two paths MUST match:** the flag makes the app write to `$(KnownFolder:LocalAppData)\hyprv`, which is exactly what the exclusion un-virtualizes. WITHOUT the flag the app writes to `<LocalCache>\hyprv` and the exclusion (targeting the real path) doesn't apply → still redirected. WITHOUT the manifest, the flag returns the real path but the write is still virtualized → UI shows the real path while the open file is in LocalCache (the exact trap seen during development; reading the env var has the same failure). Trade-off accepted: settings.json + hyprv.log are intentional persisted state, so leaving them un-virtualized (survives uninstall) is correct, not a leak. Unpackaged/Debug builds are never redirected — the flag is a no-op there.

54. **At startup, don't crash, don't hang, and don't try to INFER whether Hyper-V is "enabled".**
    - `VMManager` is a singleton built **unguarded** from `App::OnLaunched` (`VMManager::Instance()`), and its ctor opens a WMI scope on `root\virtualization\v2`. `WmiScope`'s `ConnectServer` THROWS on failure, so on a machine without Hyper-V the throw escaped `OnLaunched` and **crashed at startup**. Fix: `TryConnect()` wraps the connect + snapshot-service + subscriptions in try/catch, classifies the HRESULT (`0x8004100E` invalid-namespace → `HyperVUnavailable`; `0x80041003`/`0x80070005` → `AccessDenied`; else `Other`), records a `ConnectStatus` + message, and **does not start the poll thread** on failure. `RetryConnect()` re-attempts (the welcome page's Retry button). The welcome page reads `GetConnectStatus()` and shows an actionable panel (`allVmsError` + `OnRetryConnectClick`) instead of spinning.
    - **Do NOT gate on `Msvm_VirtualSystemManagementService` (or the snapshot service) being present** as a "is Hyper-V functional" check. A first attempt did → FALSE-POSITIVE "Hyper-V isn't enabled" on a perfectly healthy host that simply had **zero VMs** (`GetInstance` returns an empty object for that host singleton even then; user-supplied log: connect succeeded, `…ManagementService missing`). Backed out. The genuinely-uninstalled case is the `ConnectServer` *throw* above (no namespace) — that's a reliable signal; the singleton's absence is not.
    - **The poller ALWAYS fires `NotifyChanged`** (moved outside the `try { UpdateAll(…) }` in both the initial refresh and the loop), so even a poll cycle that can't fully query still leaves the UI out of "Loading VMs…".
    - **The cold-start spinner clears on first-poll-COMPLETE, not on "vms non-empty".** `WelcomePage::m_firstSnapshotRendered` is set in `OnVmManagerChanged` (which fires only from a completed poll's `NotifyChanged`); `RenderAllVms` also falls back to `VMManager::HasFirstSnapshot()`. Keying it on "non-empty" (the old bug) meant a zero-VM host spun forever. A polled-but-empty host now shows **"No virtual machines on this PC yet."**

56. **The Mica/Acrylic backdrop controller MUST be `Close()`d on the window `Closed` handler — if you leave it to the framework's own `DispatcherQueueShutdownStarting` teardown it AVs (or hangs) deep in `Microsoft.UI.Xaml` on shutdown.** Symptom: closing the app threw an "access denied"-style error box on exit (it was a `c0000005` Access Violation surfaced by WER, not a literal `E_ACCESSDENIED`). Confirmed by an unpackaged-build crash dump — the faulting thread was:
    ```
    DispatcherQueueController::ShutdownQueue
     → DispatcherQueue::StartNextShutdownStartingStage
     → ShutdownStartingCallback            (DispatcherQueueShutdownStarting event)
     → SystemBackdropInternal::BaseController::CloseInternal
     → ResetOverride → RemoveAllTargetsInternal → SetSystemBackdropOnTargets
     → Microsoft.UI.Xaml!…  mov rax,[rcx]  rcx = null+0x58  → AV (0xc0000005)
    ```
    Root cause: `MainWindow`'s `m_micaController` / `m_acrylicController` (gotcha #12 — we drive the low-level `MicaController`/`DesktopAcrylicController` directly, not the wrapper backdrops) were only ever `Close()`d inside `ApplyAppearance` on a theme *rebuild*, never at app exit. So on close the framework auto-closes the still-attached controller during `DispatcherQueueShutdownStarting`, against a XAML backdrop target that's already half torn down → null deref. (Earlier this same item was filed as an `APPLICATION_HANG` from a different user dump; same teardown path, same fix — it can present as either a hang or an AV depending on how far the teardown gets.) **Fix: `MainWindow::TearDownBackdrop()` (detach target + `Close()` + null each controller, idempotent) is now called from the window `Closed` handler BEFORE `ShutdownAllTabClients`, while the XAML target + DispatcherQueue are still alive; `ApplyAppearance` calls the same helper for its rebuild path.** General rule: any `SystemBackdrops` controller (or other COM object holding a XAML/composition target) must be explicitly closed on `Closed`, not left to dispatcher-shutdown — the framework's shutdown order tears the target down first.

## Project structure / naming

59. **Do NOT rename the WinRT projection `hyprv_app` → `hyprv`.** It was attempted once and reverted. The repo and the EXE are both named `hyprv`; the main project lives at `src/app/` (vcxproj `src/app/hyprv.vcxproj`), its `<RootNamespace>` is `hyprv_app` (matches the projection `winrt::hyprv_app::`), and its `<TargetName>` is `hyprv` (produces `hyprv.exe`). **The `_app` suffix on the projection is load-bearing.** Reason: the WinRT projection lives at `winrt::hyprv_app::` while our internal C++ code lives at `::hyprv::` (`hyprv::ipc`, `hyprv::wmi`, `hyprv::app::settings`, `hyprv::app::vm`, `hyprv::rdphost`). If the projection were `winrt::hyprv::`, then inside any `winrt::hyprv::implementation` block an unqualified `hyprv::` lookup finds `winrt::hyprv` (the enclosing namespace) FIRST, and our internal `::hyprv::` becomes unreachable without a leading `::`. MSVC reports `'app': the symbol to the left of a '::' must be a type` because it resolves `hyprv::app` as `winrt::hyprv::app`. The `_app` suffix is the standard pattern for exactly this case — a project whose root namespace would otherwise collide with its internal one. (`CLAUDE.md` carries only the one-line "do not rename" rule and points here.)
